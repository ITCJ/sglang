A

本轮实现范围与阅读顺序

2026-10-24统一页修正见本轮改动与验证清单。 以下34文件统计描述原ticket01交付范围；本轮功能修改为5个Ascend/NPU文件。 当前GLM-5.2 mempool-min默认且仅允许B=128，所有相关组件严格一致。

本轮实现 mempool-min ticket01 的冷请求路径。Main 是独立 CPU 进程；每侧 rank 0 scheduler 负责 SR 协调，每个 TP worker 执行本 rank 的分片操作。 代码已接入真实服务入口。NPU 测试由用户运行，ticket01 保持 open，后续票仍受验收门控。

本轮共 34 个文件：15 个生产代码文件、9 个测试文件、5 个配置与启动文件、5 个说明与进度文件。 生产代码中 11 个位于 Ascend / NPU 目录，4 个位于公共调用入口。

建议先看 mempool_router.py 的 submit / receive，再看 mempool_subrouter.py 的 execute / advance，最后看 native reservation 和四个主线接缝。 审核重点是资源何时实际取走、何时可读、何时实际归还。

启用开关是 SGLANG_NPU_MEMPOOL_ROUTER_CONFIG，轮次变量为 SGLANG_NPU_MEMPOOL_ROUTER_RUN_ID。 启动脚本自动设置这两项。旧正式 mempool 参考运行会清除这两个变量。

本票为 TP16 / DP1 / PP1、单真实请求、单 chunk、private replicas、greedy、无 radix。 P eager，D Graph 固定补齐 16 行；补齐行不占真实请求槽。 P alive Index K DRAM 与 prefix 的注册容量为零。

B

正常路径、数据结构和 DRAM 读取

顺序 Main / SR 的动作 可审核的完成条件
启动 BM 映射、D Graph、原生握手完成，SR 上报全组注册 两侧 16 rank 的模型、布局、会话和容量相符
reserve Main 一次扣四类额度，先 D alloc，再 P alloc SR 返回实际槽、opaque 页表、D native 行页
dispatch D 安装 P/D 绑定，再由 P 确认 两侧 ack 后才向原生 HTTP 创建匹配 Req
ready P 写回真实主 KV，SR 汇总 ready_tokens Main 发布可读位置，再通知 D
decode D 等待 Router ready 与原生 Index K / handoff 全组满足条件；P 返回的首 token 也受此门控
native cleanup P 可先清理 native；D 停止提交并 drain P 写回收据保留；D 原生页行实际归还后报 finished
free Main 归还 D native 额度，下发 P/D free SR 真实归还 alive 后才回 free_ack
完成 两侧 free_ack 收齐且 D HTTP 结果已到 账本归零、目录清空，然后返回结果并允许下一请求
数据结构 / 所在模块 内容与所有权
MainRouter.registrations 两侧完整 rank 表；实际 HBM 页、请求行、NUMA 配置、模型身份、Graph 开关
MainRouter.ledger / Quota P alive、D alive、D HBM、D row；始终满足 total = free + outstanding
active / operations / history 当前请求、op_id 回执和最近 64 个完成请求；操作回执随历史回收
directory B-token 链式页哈希、父节点、child_count、writing/ready/draining、owner hold、opaque locations
RouterShard 当前 dispatch 与 Req 的绑定；复用原有 control 的槽所有权，不另建 free list
MempoolPDControl 原生 session / attempt / lease generation 校验和真实 alive 槽归属
NativeReservation D 请求行、完整非连续 token 索引、prompt 长度、生成上限及绑定 Req
MempoolRuntime 稳定 NPU row→P/D 绑定、写回/读取事件、native 行释放后仍可用的完成收据

P 每 rank 的 BM 主 KV 是 BF16 [78,16,8192,1,576]，D 是 [78,16,128,1,576]。16 个 rank 各有私有副本，同一 NUMA 节点不表示共享。 DRAM 逻辑页与 native HBM 页统一使用 page_size=B，默认 B=128。4096 输入、上限 128 的请求 占 P 整槽 64 个逻辑页、D 整槽 1 个逻辑页、D 33 个 HBM 页及 1 行。 目录只发布实际 prompt 的 32 页，未写槽尾仅占额度。

DRAM → HBM sparse 访问仍沿用现有两次 unidexcopy kernel launch。

每层已有 materialize 逻辑先处理 HBM sparse-cache hit，再把 miss 按位置分为两路： 位置小于 prompt_len 的数据来自 P；生成段来自 D，其槽内偏移为位置减 prompt_len。 两路通过现有 NPU 映射直接填充 HBM workspace，随后合并并进入 attention。 Main 和 SR 不搬运主 KV。copy.py 与 kernel 实现本轮无改动。

新增统计只记录完成 forward 中实际提交的 P/D miss 行数，并在完成事件后读取。 它用于证明数据来源，不作为性能基准。

每个 D forward 还记录实际常驻请求数、实际执行请求数、step 和槽位关联。 验收逐 rank、逐请求、逐 step 核对两项请求数均为 1。 首 token 即结束的请求应没有 D forward，不会用 padding 行冒充真实负载。

native 预留直接调用 allocator.alloc(token_count)，保存真实非连续索引。 req_to_token 提前写入整个预留范围，Req 的有效 KV 长度仍只等于当前已使用部分。 接收 Index K 和后续 decode 均消费这些索引，不再向全局 allocator 申请。 最终在 drain 后一次归还完整预留，覆盖提前 EOS、实际尾页的未用部分和未用整页。 预留行会重置 sparse-cache 元数据，释放行仍经过原生 free hook。

P 机一条命令：

bash ascend-mempool-test/scripts/run_mempool_min.sh \
  --role prefill --mode acceptance --config mempool-min.json --run-id ticket01-001

D 机一条命令：

bash ascend-mempool-test/scripts/run_mempool_min.sh \
  --role decode --mode acceptance --config mempool-min.json --run-id ticket01-001

acceptance 自动运行 P-only / D-only / 混合复制适配器、同配置同长度的旧正式 mempool 参考、Main/SR 目标服务，再比对完整输出。四个请求依次为： 两个不同 4096-token 输入各强制 128 输出；B-token 输入实际提前 EOS；4096 输入仅输出 1 token。

正常请求通过后，入口执行一次独立 timeout / fail-stop 场景：

  1. 保存正常日志，暂停本轮启动的 P worker 进程组。
  2. 新请求让 D 实际占用 native 行页，P 的 alloc 无法完成。
  3. 等待超时，检查拒绝新请求、额度不退还、目录不变化、没有 free。
  4. 恢复 P，再清理本轮进程；两侧退出后再次检查完整 D 日志。

该场景默认额外等待一次 600 秒的 operation_timeout。 CPU 模拟已覆盖暂停、恢复、跨端协调和真实子进程回收；硬件结果待用户运行。

全流程失败即非零退出。Graph 未覆盖全 rank、缺少真实 D forward、未证明 P/D 来源、 资源未归还、未复用槽或输出不同，均不能作为通过。

常驻服务把两条命令的 --mode acceptance 改为 --mode serve，并换新的 run-id。 P 侧启动 Main 与 P，D 侧启动 D，SR 随 worker 加载。服务就绪后从 Main /generate 提交 token IDs；/status 可审查账本，忙时 429，注册不全或故障时 503。

两机的 runner 自动协调后续步骤。任一侧失败或退出，另一侧结束自身子进程。

可在启动前添加 --describe 查看配置。该模式只展示计划，不执行 NPU 验收。
