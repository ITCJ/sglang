A

阶段 0 已建立的系统与存储模型

角色分工

P 侧负责 prefill，即处理输入 prompt。 D 侧负责 decode，即逐步生成输出。 当前两侧各有 16 个计算 worker，各自组成一个 TP16 实例。 系统同时只处理一个真实请求。

角色 已实现的职责
Main Router 接收请求、检查约束、管理资源额度、匹配 prefix、编排操作和保护源数据
SR 协调者 每侧由 rank 0 承担；分发操作，汇总各分片实际完成结果
SR 分片 每个 worker 一个；解析本地映射，执行存储操作并报告完成
Scheduler 推进请求调度、模型计算和控制消息；空闲时也推进控制流程
计算 worker 执行模型计算，读写本请求需要的 KV 和 Index K

Main Router 持有逻辑位置和不透明描述符。 具体内存地址由持有映射的执行分片解析。 请求分配成功、数据写完、生成结束、资源归还分别有完成条件。

alive 与 prefix 的用途

alive 保存仍在执行的请求所需数据。 P alive 保存 prompt KV；D alive 保存 decode 产生的 KV。 请求结束且全部读写依赖解除后，alive 才能回收。

prefix 保存跨请求复用的数据，请求结束后仍可保留。 主 KV 是注意力读取的数据，Index K 用于选择相关 token。 两类数据用途不同，prefix 复用时都需要保存与恢复。

主存数据区域 阶段 0 的实际存储方式
P alive 主 KV 每 rank 一份完整副本，P 侧共 16 份
D alive 主 KV 每 rank 一份完整副本，D 侧共 16 份
P alive Index K 每 rank 一份，共 16 份
prefix 主 KV 保存在 P 侧，每 rank 一份，共 16 份
prefix Index K 保存在 P 侧，每 rank 一份，共 16 份

因此，阶段 0 的四类副本数是 16 / 16 / 16 / 16。 第一项是 alive 主 KV 的每侧副本数，其余三项均指 P 侧区域。 D 生成的 Index K 保留在计算侧缓存，不新增对应主存区域。

页与槽的实际含义

项目 阶段 0 的实现与验收配置
Token 页 每页 128 token；主存和计算侧缓存严格使用同一页大小
alive 分配 接口表达逻辑页，底层仍为请求保留整个连续槽
P alive 槽 每槽容量 8192 token，即 64 页额度
D alive 槽 每槽容量 128 token，即 1 页额度
prefix 分配 真正按页分配；每份容量 40 页，即 5120 token
数据布局 沿用 layer-first 布局

请求只用到槽的一部分时，剩余空间仍被该请求占用。 例如 4096-token prompt 使用 32 页，但 P alive 仍扣 64 页额度。 16 个 worker、16 个存储槽和计算图的补齐宽度含义不同。 这些数量不表示已经支持 16 个真实并发请求。

B

阶段 0 已完成的请求生命周期

冷请求：计算、交接、生成

  1. Main 检查输入、长度、页对齐和生成上限。
  2. Main 预留 P/D alive 额度及 D 计算侧资源。
  3. SR 分配槽位，建立请求与存储位置的绑定。
  4. P 计算 prompt，并写回主 KV 和 Index K。
  5. 原生通道完成 Index K 和请求交接信息的传输。
  6. D 在全部就绪条件满足后开始生成。

D 启动需要同时满足三个条件：

条件 含义
Prompt ready 请求 alive 内所需 prompt 数据已经完整可读
Index K ready 所有相关 rank 的 Index K 传输已完成
Handoff ready 所有相关 rank 的请求交接信息已到齐

整个计算组一致推进，单个 rank 完成不能代表全组就绪。 生成时，D 按实际选中位置读取 P 的 prompt KV 和 D 的生成 KV。

P 计算侧缓存可提前释放

P 的计算侧 KV 在必要写回和原生传输完成后即可释放。 这允许 P 计算侧资源早于 D 请求结束归还。 请求的主存 alive 仍保留，供 D 后续读取和请求结束后的保存操作使用。 P alive Index K 的保留，使后续保存不依赖已释放的计算侧缓存。

生成结束、保存完成、资源归还是三个边界

边界 已实现的含义
finished D 停止提交新工作，相关最后读写完成，必要计算侧资源已经清理
admit 完成 需要保留的 prompt 页已复制到 prefix，并按完成顺序发布
free_ack SR 已实际归还对应 alive 存储，Main 才恢复额度

Main 收到 finished 后重新检查 prefix 目录，只保存尚未存在的页。 保存前先保护源数据及必要父路径，复制实际完成后再解除保护。 prefix 目标可读后才发布，父页先于子页发布。 重复完成消息不会重复解锁、重复发布或重复归还资源。

整个 alive 槽等最后依赖解除后才能回收。 下一请求等待上一请求保存结束、全部 free_ack 到齐后再进入。 当前 Main 使用非流式接口，完整响应也要等这套流程结束。

失败时保留正确的资源状态

不支持的输入或容量不足会在入口明确拒绝，账本保持不变。 运行中出现错误或超时会进入 fail-stop，停止新请求和不安全的释放。 尚未证明读写结束的内存不会被强行归还后交给下一请求。 测试入口负责保存现场并清理本轮启动的进程。

C

阶段 0 已完成的 prefix 保存与命中

保存的内容已经包含主 KV 和 Index K。 这两类 prefix 数据以及 P alive Index K 都是阶段 0 的已有能力。 K1 的工作是改变它们的物理副本与访问方式。

命中后有两条不同的数据恢复路径

操作 数据从哪里到哪里 解决的问题
load_back prefix → P 的计算侧缓存 让 P 能接着计算未命中的后缀
fill prefix → 本请求新分配的 alive 让 D 能从本请求的存储位置读取命中段
后缀写回 P 新计算结果 → 本请求 alive 补全未命中段的主 KV 与 Index K

命中请求仍分配自己的 alive 存储。 load_back 完成后，fill 与 P 后缀计算可以独立推进。 这表示依赖允许它们并行，不代表已经量出性能收益。

ready_tokens 汇总命中段和新算段的实际完成范围。 只有从开头连续完成、且所有必要数据都可读的部分才能计入。 不能仅凭命中长度把数据标成已经写好。

完整命中仍会重算最后一页

输入完全相同，不表示这次 prefill 可以计算零个 token。 当前规则为完整 prompt 留出最后一页重算，以完成模型输出接续。 4096-token prompt 因而恢复 3968 token，重算最后 128 token。

已验收的 A → B → C → E 用例

用例 输入 实际命中 P 新计算 结束后 prefix 页数／份
A：冷请求 4096 0 4096 32
B：在 A 后新增后缀 5120 4096 1024 40
C：输入与 A 相同 4096 3968 128 40
E：另一条冷请求 4096 0 4096 40

A 保存 32 页，B 只补充此前没有保存的后缀页。 C 复用已有内容，不重复保存相同 prefix。 E 在 prefix 已满时跳过新增保存，仍正常生成并归还 alive。 容量不足时也允许缩短保存范围；当前没有缓存淘汰流程。

每份 40 页表示同一套逻辑缓存容量。 保存 16 份相同副本，并不会把可缓存的不同 prefix 扩大为 640 页。

K1 的完整目标

K1 在既有请求流程上，将主存副本改成 8 / 1 / 1 / 1。

数据类别 阶段 0 K1 默认目标 访问方式
alive 主 KV 每侧 16 份 每侧 8 份 默认每 2 个 rank 共享一份，分工写入，各自完整读取
P alive Index K 16 份 1 份 按规定分工写入，供保存和复用流程访问
prefix 主 KV 16 份 1 份 单份保存，供恢复与各 alive 副本填充使用
prefix Index K 16 份 1 份 单份保存，恢复到各计算 rank 所需的缓存

alive 的 8 份是 P、D 每侧各 8 份，并非两侧合计 8 份。 其余三项是 P 侧各一份，副本数独立于 alive 共享组数量。 每个 alive 副本不会再附带一份私有 Index K 和 prefix。 计算侧为各 rank 保留的执行缓存，不计入这四类主存副本。

物理共享必须真实成立

共享组成员访问同一份物理数据，进程内的虚拟地址可以不同。 多个 rank 放在同一个内存节点，并不自动构成共享。 分组依据实际拓扑和配置生成；双成员是默认部署，不应写成实现上限。 每个成员仍有自己的执行职责，SR 分片不会从 16 个变成 8 个。

需要区分的身份 含义
物理分配 owner 为共享区域承担实际存储分配的参与者
Writer 对某一范围执行写入的参与者
Reader 需要读取该共享区域的参与者

每个逻辑写入范围必须有明确分工，写入无遗漏、目标无重叠。 本 rank 写完自己的部分，不等于整份共享副本已经可读。 就绪与释放必须覆盖全部必要 writer 和 reader。 本步新 KV 的本地供给、历史 KV 发布以及后续读取顺序都属于正确性要求。

单份存储还需要单次源读取与广播

K1 的最终 load_back 由 rank 0 读取单份 prefix，再广播给其他 rank。 各 rank 按自己的原生映射恢复计算侧缓存。 fill 负责把命中内容写入请求需要的 alive 副本。 单读广播和多副本填充服务不同目标，不能相互替代。

副本数、描述符和容量必须一致

注册与页描述分别表达四类数据的实际副本。 容量核算根据各区域实际大小与贡献，避免把一个副本数套给全部数据。 验收核对实际分配、写入和读取证据，不能只看配置值。 共享减少主存重复存储与重复写入，并不意味着每个 reader 少读所需数据。

每张票具体做什么、如何验收

票 01：建立阶段 0 单请求性能基线

本票先量清楚当前性能，不要求先完成调优。 固定模型、输入、采样、计算图、拓扑和容量，保持真实并发 1。 覆盖冷请求、部分命中和完整命中；每类分别统计。 使用长生成负载，同时把自然提前结束的短输出单列。

指标 必须说明的口径
TTFT 后端请求开始到首次输出可用；明确观察点
ITL 同一观察点的相邻 token 间隔，保留原始样本
TPOT 后续输出 token 的平均时间，与 ITL 分布分开
后端生成耗时 后端自身请求时间，保留实际输出长度
Main 完整耗时 客户端提交到完整响应接收完毕
Main 收尾耗时 后端结果到齐到保存和释放结束

Main 完整耗时包含其前置控制与收尾，后端计时的边界更窄。 当前外部接口非流式，不能把内部输出时间叫作客户端收到 token 的时间。 已有批次刷新和直方图统计需要核对粒度，不能伪装成逐 token 原始数据。 预热、重复轮次、命中准备和计时配置都由入口自动完成并记录。 重型内容校验、故障注入和性能分析采集与正式计时分开。

验收产物是一份可重复的基线报告，附原始样本、配置和版本。 用户运行并核对测量结果后，再进入共享实现。

票 02：共享 alive 主 KV，保留已有 prefix 功能

把 P/D alive 主 KV 从每侧 16 份改成每侧 8 份。 实现实际共享建池、成员映射、分工写入、完整读取和协调回收。 P alive Index K、prefix 主 KV、prefix Index K 继续各保留 16 份。

既有流程 本票需要完成的适配
冷请求 写入共享 alive，D 读取对应共享内容并正常生成
prefix 保存 从对应共享 alive 保存到各 rank 的私有 prefix
load_back 继续从各 rank 私有 prefix 恢复其计算侧缓存
fill 向共享 alive 按组分工写，避免重复写同一目标
释放复用 等所有共享读写者完成后归还，下一请求安全复用

验收覆盖真实冷请求、B/C 命中、内容、计算图和槽复用。 不能只在关闭 prefix 的配置下证明本票通过。 内存占用与分配贡献应证明默认主 KV 确实变为每侧 8 份。

票 03：Index K 与 prefix 各改为单份

把 P alive Index K、prefix 主 KV、prefix Index K 从各 16 份改为各 1 份。 同时修改区域映射、写入职责、注册信息、目录描述和容量核算。 保存流程保持源保护、目标完成后发布及正确释放顺序。

本票的过渡读取方式为：各 rank 都读取同一份 prefix。 每个 rank 用它恢复自己的计算侧缓存，命中功能始终可用。 主存中只有一份源，不能保留隐藏私有副本来实现读取。 fill 仍负责补齐各必要 alive 副本。

验收同时覆盖保存和 B/C 命中，证明 8/1/1/1 真实成立。 本票完成后，存储副本数达到最终目标；单次源读取尚待票 04。

票 04：单次读取 prefix，再广播

将票 03 的重复读源改为 rank 0 读取、组内广播。 各 rank 接收后，按自己的原生索引恢复计算侧缓存。 所有必要接收与恢复完成后，才能报告 load_back 完成。 随后仍按现有流程推进 fill、后缀计算、D 生成与回收。

验收证明源端只按计划读取一次，其他 rank 通过广播取得内容。 分别核对广播内容、恢复映射及延迟成员的完成约束。 不能仅凭存储只有一份，就认定已实现单次读取。 本票不以服务吞吐提升幅度作为关闭条件。
