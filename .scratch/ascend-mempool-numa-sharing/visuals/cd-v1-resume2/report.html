A

先看三个结论

共享写入的主要收益来自去重

36 MiB 逻辑任务下，TP4 共享池耗时约 0.522 ms。 TP4 集中配置的独立池耗时约 2.081 ms。 共享池用约四分之一的实际拷贝量，取得约 3.98 倍完成速率。

问题 这组结果给出的答案
TP4 共享写入比 TP2 快多少？ 36 MiB 下约快 1.1%～1.4%；两者都约 0.53 ms
等实际拷贝量时，共享池还有巨大优势吗？ TP4 两者都约 0.522 ms，P50 差异不足 0.1%
四个 rank 读同一份 KV，是否只搬一次？ 每 rank 都读完整 KV；batch=16 合计搬运 144 MiB
TP4 共享读取是否明显快于集中独立池？ batch=16 下，三种来源的组 P50 差异均不足 0.4%
哪个配置的吞吐增长最明显？ 分散配置 4-ID：大块写入约 260 GB/s，本地读取约 350 GB/s
NUMA 结论仍有边界

162 行的 numa_verified 均为 false。 本文的“集中 / 分散”均指请求的分配配置。 这些数值可用于配置对比；物理 NUMA 落点仍待证明。

P 和 D 是运行测试的主机角色。它们的结果均为 copy 组件计时。 每次只让一侧的 rank 组发起读写，对侧维持池可用。

I0 = 每 rank 独立池，全部请求 node 0。S0 = 多 rank 共享 node 0 的一个池。 ID = 每 rank 独立池，分别请求不同节点。 容量按实现的分配规格列出；它不是逐页驻留测量。

每行 KV 为 576 个 BF16，即 1152 bytes。只测一层。

工作量定义 独立池每 rank 共享池每 rank 整组实际字节数
C：同一逻辑任务 L 写完整 L 写互不重叠的 L/N 独立 N×L；共享 L
C：等拷贝总量 L 只写自己的 L/N 写互不重叠的 L/N 都为 L
D：同索引 sparse 读取 读自身副本的完整结果 读共享副本的完整结果 都为 N×读取结果

C 主实验的 L 为 2048、8192、32768 行，即 2.25、9、36 MiB。 共享目的地互不重叠：TP2 每 rank 写一半，TP4 每 rank 写四分之一。

D 从每请求的 65536 行中取 topk2048。 所有 rank 使用同一组索引及顺序，分别写入各自 HBM。 batch=1 每 rank 读 2.25 MiB；batch=16 每 rank 读 36 MiB。

local 指本机；remote 指另一台主机；mixed 指每侧各 1024 行。 remote 与同机跨 NUMA 访问是两个不同概念。

G

如何使用这些结论

目标 本次结果支持的选择 仍需保留的条件
减少副本及写入流量 共享池；TP4 写入一份，配置容量从 8 降至 2 GiB 读输出仍需每 rank 一份
提高本地并发读取吞吐 分散独立池配置的结果更好 增加副本容量与重复写入量
固定总字节数的写入 分散配置具有更高有效吞吐 独立池分片对照不构成完整副本更新
决定模型服务最终策略 把本页作为组件证据 还需真实服务测试及物理 NUMA 证据

计时口径：同机组完成包络 ÷ 64。 包络为最后完成时间减最早开始时间。 它包含 Graph 提交、执行和完成等待。 源数据准备、地址分片、初始化与 CPU 校验不在计时区内。 这里没有计入完整 materialize、attention 或模型请求耗时。

P50/P95 来自 60 个批次的均摊时间。 它们不是单个请求或单次 replay 的尾延迟。 表中的 P / D 分别来自两侧，未合并分位数。

带宽直接采用 CSV 的中位数；单位为 GB/s，1 GB = 10⁹ bytes。 CSV 字段名虽含 gbps，数值表示字节速率。 它是有效 copy 吞吐，不是硬件链路计数器测出的总流量。

本页只收到汇总 CSV，没有逐轮原始样本。 不能由这些分位数计算置信区间，也不把微小差异称为统计显著。 各项报告的启动偏差 P95 最大约为 3.35 μs。 这个指标来自主机提交时间，不能证明每条 DMA 的重叠区间。

64 次 replay 复用同批索引；下一批切换索引。 没有应用层 selected KV 缓存复用，但未证明硬件缓存为冷态。 未测试“共享一份 KV、同时分布于多个 NUMA 节点”的混合布局。 共享 ticket 的最终验收状态仍保留为待确认。
