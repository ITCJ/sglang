8 个 NUMA 实际覆盖哪些地址

所有区间统一采用 [起点, 终点)。 它包含起点，不包含终点；字节数等于终点减起点。 地址以十六进制表示，数值越大，越靠地址轴右侧。

Linux 节点 起点，包含 终点，不包含 内存块覆盖大小
node0 0x28000000000 0x2c000000000 256 GiB
node1 · 低地址段 0x40000000 0x80000000 1 GiB
node1 · 主区间 0x24080000000 0x28000000000 254 GiB
node2 0xa8000000000 0xac000000000 256 GiB
node3 0xa4000000000 0xa8000000000 256 GiB
node4 0x128000000000 0x12c000000000 256 GiB
node5 0x124000000000 0x128000000000 256 GiB
node6 0x1a8000000000 0x1ac000000000 256 GiB
node7 0x1a4000000000 0x1a8000000000 256 GiB

node1 是唯一包含两段的节点。 它的低地址段位于 [1 GiB, 2 GiB)。 主区间位于 [2306 GiB, 2560 GiB)。 两段合计 255 GiB；中间的大跨度不算 node1 的内存容量。

相邻编号不代表地址顺序相同。 每组都是奇数节点的主区间在前，偶数节点在后。 例如，node1 主区间的终点恰好等于 node0 的起点。

本次 memory block 大小是 1 GiB。 表格表示在线内存块覆盖范围，块内可能仍有保留区或空洞。 这些范围不能直接替代 MemTotal 或 MemFree。

C

4 个 Fabric 窗口覆盖哪些地址

这里用 W0～W3 标记驱动数组中的四个窗口。 窗口编号与 Linux NUMA 编号没有同名对应关系。 例如，W1 在这台机器上重叠的是 node2。

公开驱动的窗口长度是 0xaa80000000 字节，即 682 GiB。 每个窗口的终点都由“起点 + 682 GiB”得到。

窗口 起点，包含 终点，不包含 窗口长度
W0 0x29580000000 0x34000000000 682 GiB
W1 0xa9580000000 0xb4000000000 682 GiB
W2 0x129580000000 0x134000000000 682 GiB
W3 0x1a9580000000 0x1b4000000000 682 GiB

窗口描述允许搜索的地址范围。 一个窗口覆盖 682 GiB，并不说明这 682 GiB 都装有在线 RAM。 实际候选内存还必须落在 Linux 的物理内存范围内。

E

170 GiB 如何逐步算出来

对一个 NUMA 区间 N 和一个窗口 W，先比较端点：

交集起点 = max(N 的起点, W 的起点)
交集终点 = min(N 的终点, W 的终点)

若交集起点 ≥ 交集终点：交集为空
否则：交集大小 = 交集终点 − 交集起点

以 node0 和 W0 为例：

node0 = [0x28000000000, 0x2c000000000)
W0    = [0x29580000000, 0x34000000000)

交集起点 = 0x29580000000
交集终点 = 0x2c000000000
交集大小 = 0x2c000000000 − 0x29580000000
         = 0x2a80000000 字节
         = 170 GiB

node0 和 W0 各自可分为两段：

对象 窗口或节点之外的部分 共同覆盖的部分 合计
node0 前 86 GiB 位于 W0 之前 后 170 GiB 落入 W0 256 GiB
W0 后 512 GiB 超出 node0 终点 前 170 GiB 落入 node0 682 GiB

W0 的后 512 GiB 没有重叠这份清单中的在线内存块。 它不能算作 node0 的额外内存。

再看 node1 主区间与 W0：

node1 终点 = 0x28000000000
W0 起点    = 0x29580000000

node1 终点 < W0 起点
因此：node1 ∩ W0 = 空集

node1 的低地址段距离 W0 更远。 其他窗口的地址都比 W0 更高，因此也没有交集。 node3、5、7 同样在各自附近的窗口起点之前结束。

G

这些交集怎样影响 MF 分配

在公开驱动的这条 Fabric 分支里，分配器先限制搜索范围。 它只在指定 NUMA 与允许窗口的交集内尝试取页。

对奇数节点：交集已经为空。 换成 2 MiB 页仍然没有候选地址。 指定 NUMA 的这条路径不会自动换到其他节点。 这解释了 1 GiB 页和 2 MiB 页都快速返回失败的现象。

对偶数节点：170 GiB 只是范围上限。 实际取页还受占用、保留区、连续页和迁移条件影响。 节点整体的 MemFree 和 buddyinfo 不区分窗口内外。

以下是一个说明“总 free 不够判断”的假设例子：

区域 地址范围容量 假设空闲量
窗口外的前 86 GiB 86 GiB 86 GiB
窗口内的后 170 GiB 170 GiB 64 GiB
整个偶数节点 256 GiB 150 GiB

这个例子中，系统显示 free = 150 GiB。 MF 候选范围内只有 64 GiB 当前空闲。 仅靠这些空闲页，无法满足 88 GiB 合计需求。 回收或迁移其他页面，可能改变可分配容量。 表中空闲量是示例，不是本次实测值。

按当前模型参数，单 rank 原始池是 21.9375 GiB。 池大小按整 GiB 向上取整后是 22 GiB。 4 个 rank 放在同一节点时，合计需要 88 GiB。 它们通常是四次独立申请，不是一块 88 GiB 连续物理内存。

哪些已经证实，哪些还需核对

层次 当前结论
实测地址 31 上的在线内存块范围由你的 sysfs 输出给出
精确计算 对本页列出的四个窗口，偶数节点各重叠 170 GiB
精确计算 对这四个窗口，所有奇数节点的交集都是 0
运行现象 你的 node1 小池分配快速失败，node0 和默认策略成功
版本核对 仍需确认 SPC009B220 使用相同窗口和分配分支
大池失败 仍需确认窗口内占用及连续页条件，不能只归因于碎片

这里的偶数、奇数规律来自这台机器的地址布局。 不要把 Linux 节点编号的奇偶性当成通用硬件规则。 32 机器也应按自身的物理地址分布计算。
