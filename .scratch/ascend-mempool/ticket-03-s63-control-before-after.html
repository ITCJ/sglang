这次提交到底改变了什么？

环节 提交前 提交后
service 查一个请求 生成全部记录的快照，再筛选 按完整 identity 直接取一条快照
service 尚未取得 identity 在全部快照中按 room 查找 通过当前 room owner 定位

TP 交换内容 完整 control 快照和消息对象 逻辑状态、事实与消息摘要
同一 tick 内读取 多处重复生成全量快照 复用本轮观察，日志按 identity 查询
preflight 复制全部记录后试执行 仍复制全部记录后试执行

生产修改集中在三个文件。service 收集请求事实；control 管理生命周期；tick 协调同侧 TP 决策。

这次提交没有修改 KV 搬运算子。删除统计、共用 row 推导属于前两个提交。

例子一：256 个旧请求，只查当前这一个

**示意场景：**control 留存 256 个已结束请求，另有请求 A 正在 decode。service 现在只想知道 A 的状态。

下面是简化后的调用逻辑。

# 提交前：service 的查询路径
for request in control.snapshot().requests:
    if request.identity == identity:
        return request

# 提交后：只构造目标请求的不可变快照
return control.get_request(identity)

新查询平均为 O(1)，旧路径为 O(N)。这里的 N 包括留存的历史请求。

RequestIdentity 包含 room、attempt、P session 和 D session。已有 identity 时，查找必须完整匹配。

尚无 identity 时，get_room_request(room) 查询当前 owner。它不会随便选取这个 room 的某条历史记录。

查询接口的边界

变化针对 service 原先“全量快照后筛选”的路径。返回值仍是快照，service 不能直接修改 control 内部记录。

C

“分离活跃与终态”是不是拆成两个字典？

没有拆成两套请求状态。_records 仍是统一的记录存储。新增索引用于快速选出不同用途的记录。

control
_records活跃记录与近期终态记录，统一存储
_active_requests仍需协议推进的 identity 集合
_room_ownerroom 当前归属的 identity
_room_record_countsroom 是否还有留存记录

snapshot() 保留完整诊断视图。active_snapshot(include) 生成调度视图；include 补入本轮本地清理所需的 identity。

请求示例 当前状态 是否参与普通协议推进 是否保留记录
A DECODING 是 是
B WAITING_RELEASE_ACK 是，即使本地 slot 已释放 是
C CLOSED，但本地 Req 尚未移出队列 作为可选清理记录加入本轮 是
D CLOSED，本地也已清理完 不随普通调度反复传递 在有界历史中继续留存

终态淘汰时，control 同时维护这些索引。历史留存仍服务于重复、迟到消息处理。

例子二：slot 空闲，不代表协议结束

D 已释放本地 slot 并发送 DONE，正在等 P 的 RELEASE_ACK。此时 B 仍属于活跃协议请求。若把“无 slot”当成“无工作”，确认流程就可能停止推进。

D

TP 同步具体精简了什么？

这里的 TP 同步是同一侧各 rank 之间交换调度信息。P→D 的 Index K 传输、远端 KV 读取是另一条路径。

需要同侧共同决策的内容 提交后的表示
请求身份与阶段 room、attempt、phase
slot 是否属于该请求 slot、generation、owns_slot
是否可以开始或结束 绑定、传输、写入与释放事实
容量与错误 可用 slot、peer 是否就绪、fault
收到什么协议消息 消息种类、room、attempt、长度和 slot 摘要

完整 peer layout、各 P/D pair 的 session 和 proof 不再放进 TP 观察载荷。原始消息仍保留在本 rank，交给 control 做完整校验。

**仍有三次 collective：观察、预检结果、提交结果。**此次减少的是载荷和重复取快照；没有把协议简化成一个 KVPoll 状态。

例子三：slot 复用后，旧 DONE 到达

**示意场景：**请求 A 使用 room=41、attempt=a、slot=0、generation=7。A 正常结束后，请求 B 使用 room=42、attempt=b，复用 slot=0、generation=8。

提交前 提交后
普通 tick 也传递 A 等留存记录 普通 tick 主要传递 B 等活跃记录
control 按原协议校验旧消息 control 仍按原协议校验旧消息
历史记录出现在完整 TP 快照中 A 的消息摘要参与决策，原始消息在各 rank 本地校验

防止旧消息误释放新 slot 的要求，前后都存在。此次保留 session、generation、retirement、绑定证明及所有权校验。

历史已淘汰时，也继续走原有旧消息处理规则。测试覆盖了部分 rank 先淘汰历史的情况。

F

为什么还需要“可选终态清理记录”？

各 rank 的本地队列不一定在同一 tick 移除已结束 Req。

同一个已结束请求 rank 0 rank 1
control 协议状态 CLOSED CLOSED
本地服务队列 已移除 Req 仍有 Req 等待清理
本轮附加的终态快照 无 有

如果把两边整个调度视图强制比较相等，就会误报 TP 分歧。

提交后，活跃协议状态必须一致。可选终态清理记录则合并；同一记录在多处出现时仍检查冲突。

已 native_free 的旧事实不能触发新 admission。另一个边界是 P 已处理 ACQUIRE/CANCEL，HTTP 请求随后才到达。

这时 room 已无当前 owner，但仍留存终态记录。service 会让迟到请求进入取消清理，避免一直等待绑定。

这些处理用于保持原有取消和清理语义，防止精简视图引入回归。

场景固定为一个活跃请求。458 B 是该微基准的观察载荷，不是所有服务请求的固定大小。

“完整快照”列测量保留下来的 snapshot() 接口。它展示全量复制成本，不等同于提交前服务端的完整耗时。

不能据此说“整个 tick 已与历史数量无关”

preflight 仍复制全部请求记录和相关索引。接近留存上限时，这项成本约为 11.5 ms。局部复制或写时复制需要单独设计与验证。

这些结果证明查询和载荷规模得到控制。它们不包含真实 TP 通信、NPU 或网络耗时，不能换算成服务 TPOT 收益。
