对 proof 校验，你的提议成立

各 rank 先检查自己的原始消息，再把结果与消息摘要一起同步。结果必须绑定具体消息、请求及本轮状态。

示例 本地校验结果 第一次同步后的决定
rank 0–14 的 DONE 正常 通过 等待全组结果
rank 15 的 DONE 证明错误 错误 全组停止本轮提交

现有测试用 rank 15 的错误 proof 验证“所有 rank 都不推进”。这项要求可以由第一次同步实现。

**这个例子不能证明必须另开一轮 preflight 同步。**此前用它解释独立同步的必要性，并不充分。

当前三轮与拟议两轮有什么区别？

次序 当前实现 可以评估的改法
同步前 收集事实和消息摘要 校验原始消息，准备候选动作及约束
第一次同步 交换观察，形成共同计划 交换观察及准备结果，形成共同计划
计划形成后 在 control 副本上试执行整份计划 仅组合已验证、彼此兼容的动作
提交前同步 交换 preflight 结果 满足完整覆盖条件后，可删除此轮
实际提交 执行状态转换与本地副作用 执行状态转换与本地副作用
提交后同步 全组成功后才发送 outbox 仍保留

当前共同计划生成后，才执行本地完整校验。其他 rank 必须知道该校验是否失败，因此当前代码需要中间一轮。

若能把所有预期协议拒绝条件提前覆盖，就可以评估从三轮减为两轮。

C

为什么只加一个 proof_ok 还不够？

proof 说明这份绑定来自相应的分配过程。它不保证当前阶段允许执行消息。

**代码中的例子：**P 已签发合法 proof，但仍处于 ACQUIRED，尚未收到 BOUND_ACK。此时普通 DONE 仍会因阶段不匹配被拒绝。

仍需检查的内容 当前主要检查位置
session 与绑定是否匹配 control.apply 及绑定检查
当前 phase 是否允许消息 各消息对应的状态转换
淘汰历史后的旧消息能否接受 退役 generation 与所有权检查
新请求是否能进入 room 归属、记录容量、slot 检查
多个动作组合后能否执行 当前 preflight 按计划顺序试执行

上述检查中，一部分可以在本地提前完成。依赖共同计划的部分，要由共同规划器根据充分的约束完成。

不能只验证多个动作各自合法，就假定它们一起合法。例如两个动作可能竞争同一项有限资源。

D

我建议的设计方向

  1. 在 control 内准备候选动作，返回结果与资源约束。
  2. 第一次同步一起携带这些结果和现有观察。
  3. 共同规划器选择合法动作，并处理整批资源冲突。
  4. 使用准备时的稳定状态提交，新的协议消息留到后续 tick。
  5. 保留提交结果同步，全部成功后再发送 outbox。

准备结果要区分可执行、等待、合法旧消息和错误。不同 rank 留存的历史可能不同，应比较行为是否兼容。

校验逻辑应由 control 统一维护，避免在 tick 中复制第二套规则。候选参数、动作顺序和状态稳定性也需要明确保证。

判断

我支持朝减少一轮同步的方向设计。proof 校验无需单独一轮；当前整套 preflight 的替代方案，需要覆盖它承担的其他检查。

减少同步和减少全量复制是两项收益，需分别测量。现有 CPU 微基准不能推算少一次真实 TP collective 的收益。
