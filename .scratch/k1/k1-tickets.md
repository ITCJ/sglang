## 1 术语

| 术语 | 含义 |
|---|---|
| 组 k、owner、成员 | 分组 {2k, 2k+1}，k = 0…7，P、D 两侧成员编号一致；owner 是组内第一个 rank（2k），负责分配、绑定 NUMA 和注册该组的共享区域；成员指组内两个 rank |
| 共享池适配器 | 组件实验里的跨进程多参与者共享池：member 0 分配整段，其他成员贡献 0，各进程各自映射 |
| share=0 / share=1 | 适配器开关：每 rank 独立池 / 同组 rank 共享一份 |
| 预重构 | 行为不变、只为让后面的票变薄的改动：覆盖位图、读者计数、多成员会话接口，都先以退化形式落地 |
| 段 | 单份 prefix 池按 NUMA 切成的 8 块，段 k 在 NUMA k，owner 是 rank 2k |
| 起始段 | 一个请求 admit 时第一页落的段，之后按页轮转 |
| 读者分配函数 | load_back 时把命中页分给各 rank 的函数，输入页描述符列表，输出每 rank 的页列表；做成配置 |
| prefix split_read | C100：命中页分给组内各 rank，各 rank 读自己那份进 HBM，all_gather 成全集，各自按原生映射恢复；完成 = 所有 rank 恢复完 |
| numa interleave | C101：admit 分配连续页时在 8 个段之间轮转，使同一请求的页散在各 NUMA；只改分配器选页，不改链式哈希和 place(hash) |
| 全员集合通信 | all-reduce、all_gather 这类“每个 rank 的完成都依赖全部 rank 已进入”的组内通信；broadcast 不算 |
| 覆盖位图 | 协调者按副本记的“哪些页已写完”位图；单写者时等价于原来的连续计数器，双写者时由两个分片的报告合并 |
| 读者计数 | 协调者按副本记的“还有几个读者没停”；计数归零才对 main router 发 free_ack |
| 页驻留证据 | 用 numa_maps 或 move_pages 抽样核对一段内存的页实际落在哪个 NUMA |
| applied / planned | 规划器报告的状态：生产按映射文件启动且逐 rank 注册快照等于映射文件为 applied；只有规划为 planned |
| 汇总缓冲 | 票 03 每层复用的一块连续 HBM，16 × B 个槽位，一槽一页，B = ceil(命中页数 ÷ 16)；主 KV 与 Index K 各一块；没有独立暂存区和重排缓冲（2026-10-30） |

| 散开 | 一个按行索引的拷贝核按槽位表把汇总缓冲写到 HBM 页，主 KV 同时拆回 512 / 64 两个缓冲 |
| CPU 映射、GPU 注册 | 进程 mmap 共享段供 CPU 拷贝；cudaHostRegister 之后 GPU 才能直接读写它 |
| 哨兵校验、负测试 | 读对方写的那部分并和本地 HBM 里的同一数据比对；负测试指故意拖慢对方写回，看机制是否仍能挡住早读 |

## 3 共同规则

1. 每票交付 = 代码 + 验收入口（A / B / C / E 与 V1–V10，按票调整的条目在各票写明）+ perf 子模式基线表 + 证据归档 + 拓扑快照。
2. 基线表与票 01 并列，每段报 n、p50、min、max，T_step 另加 p90、p99。不设性能门槛；变差超过轮间波动要写原因；自动报告的 max ÷ min > 1.5 规则保留，接受与否由用户人工判定，和票 01 一致。
3. 每票重报三项基线遗留：A 比 E 多出的时间及其落点（基线 A 多约 5.2 s，其中 gen 多约 4 s，落在 handoff 附近）；C 的 fill 长尾（基线第 5 轮 781 ms）；每请求 forward 步数（基线记 128）。它们由旁路票 X 定位，各票只重报不处理。
4. 中间版本都要保持第 0 节的“每个中间版本都保持”一行；任何一项退化即票不关闭。
5. 配置化：分组、owner、写分工（P 按页、D 按特征维或按层）、读者分配函数、起始段策略、admit 执行者（并行 / 单 rank）、Index K 写者都做成配置，默认值见各票；不写死“各写一半”。
6. 集合通信只在有序的调度 tick 里发起（M26）；网络接收线程只入队。

## 5 票 01：K1-02a 显式映射启动与页驻留证据

**目标**：让“每份副本放在哪个 NUMA”成为启动时给定、注册时上报、运行时可核对的事实；为后面所有共享区域的放置证据打底。

**改动**

- 生产启动读取 {host, rank, node} 映射文件；每 rank 按映射绑定自己的池；拒绝不合法的映射（节点不存在、rank 重复、缺项）并给出拒绝码。
- 注册上报每份副本的 NUMA 和 owner（此时 owner 就是自己）；规划器报告状态由 planned 改为 applied，定义是逐 rank 注册快照等于映射文件。
- 页驻留抽样：每份副本抽样页实际落在配置的 NUMA；每 NUMA 常驻内存等于两份私有副本。

**验收**

- 默认映射（现状的连续映射）：A / B / C / E 与 V1–V10 全过，基线表每段在轮间波动内。
- 另一个合法映射（例如把两个 rank 的副本换到别的节点）：同样全过，驻留抽样跟着映射走，证明映射真的生效而不是恰好等于现状。

**证据**：applied 报告；两种映射下的驻留抽样；基线表并列。

## 7 票 03：K1-04 prefix split_read（16 份布局）

**目标**：在每 rank 一份 prefix 的现状上实现分工读加 all_gather（C100），把读路径先做对，让 08 去副本时只换读者分配函数。只依赖 01 基线，可与 01、02 票并行开发。

**做法**（2026-10-30 改为合并缓冲做法，会话里叫甲；原来"暂存区、all_gather 汇总、按页重排、散开"的四跳写法作废。实施侧 2026-10-29 按旧写法做过一版，按本节改）

- 读者分配函数：输入命中页的描述符列表，输出每 rank 的页列表。默认轮转：第 i 页给 rank i mod 16；可配；页数不整除时各 rank 补齐到块长 B = ceil(页数 ÷ 16)。
- 汇总缓冲：每层复用的一块连续 HBM，16 × B 个槽位，一槽一页，槽位号 = rank × B + 页在该 rank 列表里的序号。主 KV 一块，每行 compact 576 维；Index K 一块更小的，每行 256 B；两块槽位顺序相同。没有独立暂存区，没有重排缓冲。
- 槽位表：槽位行到 HBM 行的映射，每 rank、每次恢复建一次，所有层共用；主 KV 与 Index K 共用一张（【实施侧】分配器一次给出同一份 token 行索引 indices，主 KV 的 512 / 64 两个缓冲和 Index K 都用它，三者 page_size 相同，页号和页内偏移一致）。表就是 indices 的一次重排加截断：槽位 s 放逻辑页 p，则槽位行 s × 128 … s × 128 + 127 对应 indices[p × 128 … p × 128 + 127]；补齐槽位不生成行。
- 每层三步，全在恢复 stream 上按序进行：
  1. H2D：本 rank 把分到的页从自己那份 prefix 直接读进汇总缓冲里属于本 rank 的那一段（槽位 rank × B 起），compact 原样放，一次发射。
  2. in-place all_gather：输入是本 rank 那一段，输出是整块缓冲；做完后各 rank 的缓冲内容相同，补齐槽位里是垃圾。
  3. 散开：一个按行索引的拷贝核按槽位表把槽位行写到 HBM 行，主 KV 每行前 512 维进 512 缓冲、后 64 维进 64 缓冲，Index K 整行写入。原生映射和拆两个缓冲在这一步一起完成，数据不需要先按页排好。
  Index K 只在 21 个 producer 层做。两块缓冲层间复用；若要让下一层的 H2D 与本层的 all_gather 重叠，可各开两块轮换，本票不要求。
- extend 仍等整段完成，按层流水留阶段 2（C51）。
- 集合通信只在有序调度 tick 里发起；协调者在所有 rank 散开完之后才对 main router ack（op2 对 main router 仍是整段完成）。
- 主线先例：page-interleave 池（page_interleave_pool）用同样的 in-place 常规 all_gather 加索引表，不做重排，写法可参照。

**不变**：副本数不变；op1、op3 不变。

**验收与证据**

- B、C 命中，V1 / V3 / V6 / V7；V2 的内容核对改为：all_gather 后的汇总缓冲和散开后的 HBM 页都与本 rank 私有副本逐 token 一致，主 KV 和 Index K 都比（私有副本是 08 之后不再有的对照源，本票必须用上）。
- 每 rank 读取字节计数：每页恰好被一个 rank 读一次，总和等于命中页字节。
- 恢复路径每层每类只有 H2D、all_gather、散开三步；恢复用的 HBM 临时缓冲只有两块汇总缓冲，大小 = 16 × B × 页字节，首次恢复时打一行日志。
- 槽位表每次恢复只建一次、主 KV 与 Index K 共用；4K 配置命中 31 页不整除，rank 15 的第二个槽位是补齐，散开必须跳过它，由 V2 的逐 token 比对覆盖。
- ack 时刻晚于最后一个 rank 散开完成。
- 分配函数换成另一种（例如连续块）时结果不变，只有槽位表变、三步不变，证明分配是配置而不是写死。

**基线表重点**：T_lb_rank、op2，并把 op2 拆成 H2D、all_gather、散开、控制四段各报一行；这组数决定要不要再做直接落原生页的两种做法（按页 broadcast 到原生页、peer write），它们留作后续优化，本票不做。4K 配置下 op2 约 100 ms 读约 373 MiB，由分段数和控制开销主导，预期本票基本不动 op2；不设门槛。

## 10 票 06：K1-03b D alive 主 KV 共享与每步顺序

**目标**：D 侧 share=1：组 k 两个 rank 共写一份 alive 主 KV，每步各写新 token 的一半，下一步读对方写的那一半正确。不依赖 P 侧共享。

**写分工**：两个成员按特征维切（C67）：每层算完，新 token 这一层的 576 维切两半各写一半；可配为按层切。两半是不相交的字节范围。读者是本组两个成员的 swap_in；读者计数为 2。

**每步顺序（默认写法）**

要保证的只有一句：第 t 步两个成员写的全部内容，在任一成员第 t+1 步的任何一次 swap_in 之前已落到 DRAM 并对对方可见。新 token 本步的 KV 不从 DRAM 读，所以读写冲突只跨步。

规则：

1. 写回必须排在本 rank 本层第一次全员集合通信之前。写回和 forward 同流时天然成立；写回走单独的流时，compute stream 在发起本层 attention 输出投影后的 all-reduce 之前等写回的 event。
2. 读取沿用现状，不加任何等待。

依据：全员集合通信里 rank A 的 kernel 完成，意味着对方已进入这次通信，而对方进入之前，它流上排在前面的写回已经完成；A 第 t+1 步的 swap_in 要用本层 top-k 的结果，必然排在 A 第 t 步所有 all-reduce 之后。不加跨进程消息、不加共享内存标志。

放宽版本（备选，T_step 超出轮间波动时启用）：不按层等，在本步最后一次全员集合通信之前等齐本步全部写回。

票内必须验证：

- 现在 D 的写回走哪条流、是 memcpy 还是能入图的写 kernel；单独流且无 event 依赖就加规则 1 的等待。
- 所依赖的通信必须是全员的；broadcast 的完成只依赖根 rank，不能当顺序点。核对本步最后一次集合通信是哪种。
- 跨 GPU 经主存的可见性用哨兵校验实际证明：debug 模式下第 t+1 步开始前，本 rank 从 DRAM 读回 token t 整行，和自己 HBM 里的 token t 比对，不依赖 top-k 是否选中它。
- 负测试：在对方写回流里注入延迟，关掉等待应当失败、打开应当通过。
- 图捕获：写回和 event 在 Graph replay 的捕获范围内，校验在 replay 模式下跑。
- 覆盖检查：每份副本两个写者的范围并集等于整行、两两不相交，静态算一次，运行时字节计数核一次。

**验收与证据**：A / B / C / E 与 V1–V10；V4 加“读对方 rank 写的 token 的最早一步”（第 1 步读位置 prompt_len）；注册快照 R_am(D) = 8；D 每 NUMA 常驻内存等于 1 份副本；哨兵每步校验与负测试通过；replay 模式通过。

## 16 票 12：K1-05d 主存五类区域改 page first（布局正确性，行为不变）

加票日期 2026-11-01（用户决定；票的方案以设计侧为主，实施侧 2026-11-01 的现状与建议稿作为事实基线）。位置：08 验收后、11 之前；Blocked by 08，阻塞 11（09 经 11 传递依赖 12）。理由：票 11 要按整页块搬运，layer-first 下每页主 KV 78 段加 Index K 21 段；若 11 先做、布局后改，搬运路径要重做一遍。M17 暂缓 page first 的理由（减少阶段 0 的改动）只对阶段 0 成立，完整定稿本来就是 page first（C28、C32）。

**目标**：五类主存区域（P alive 主 KV、D alive 主 KV、P alive Index K、prefix 主 KV 8 段、prefix Index K 8 段）全部改为 C32 的页 → 层 → token 排列；现有服务路径（P 写回、D 逐步写回、D 稀疏读、op1 fill、op2 load_back、op3 admit）在新排列上行为不变；给出可核对的整页块接口供票 11 接入。HBM 原生布局（主 KV 512 / 64 两个缓冲、Index K 页、attention 缓冲）不变：设备侧仍是每层一个张量的 layer-first，两种排列的差别只在拷贝的地址计算里（主线 HBM ↔ host 的 lf / pf kernel 就是这样做的）。

**现状（实施侧 2026-11-01）**：按页管理已经到位（统一 B = 128；alive 整槽预留、逻辑页 = 槽 × 64 + 槽内页；prefix 真正按页分配，40 页 8 段各 5 页，物理页编码 段 × 5 + 段内页，按段轮转、段满取最空），但存储排列仍是 layer-first：alive [层, 槽, 槽内 token, head, feature]，prefix 段 [层, 段内页, 页内 token, head, feature]，单页跨层不连续，段内每层 stride 按 5 页算；五类区域各自独立，主 KV 与 Index K 分区。池间 copy 逐层调用按 token 行索引的拷贝接口（批量行索引），布局检查限定单行 ≤ 32 KiB、单层跨度 ≤ UINT32_MAX；P 每层 144 MiB，完整 P 主 KV 区域约 10.97 GiB。fill / load_back 用独立设备流、仍由 worker 的有序执行路径提交；admit 在调用流提交；三类操作用事件查询完成。

**排列（C32 page_first_direct；两类数据分区，同一逻辑页对应两个连续块）**

- 区域 = [物理页, 层, 页内 token, head, feature]。令 L 为区域层数（主 KV 78、Index K 21）、r 为每 token 行宽（1152 B、256 B）、B = 128：page_bytes = L × B × r，主 KV 每页 M = 11,501,568 B，Index K 每页 I = 688,128 B，合计 12,189,696 B。
- alive：物理页 = 槽 × (S ÷ B) + 槽内页（S_P 每槽 64 页；S_D = 128 每槽 1 页，物理页 = 槽号）；页归属仍由槽换算，不引入散页分配器。
- prefix：每段一个区域，物理页 = 段内页（5 页）；段号与段内页的描述符编码、分配规则不变。
- 地址 = 区域基址 + 物理页 × page_bytes + 层 × B × r + 页内 token × r + 行内偏移；D 的特征分写就是行内偏移加宽度。页内无额外 padding；区域大小 = 页数 × page_bytes，探针区与库要求的对齐照旧另算。
- 只保留 page first：不设生产配置开关，layer-first 公式不进服务代码；布局类型、B、各维度进注册 / describe 与启动一致性签名，布局不同的进程启动即拒绝。重启重建临时池，不做在线迁移。

**改动**

1. 先验证拷贝接口（本票第一步，结果归档为第一份证据）：用小几何和真实 P 几何（跨度 > 4 GiB）核对现有按 token 行索引的拷贝接口能否安全接受 page first 的行集（同一层跨页 stride = page_bytes）。默认方案是分段基址：每次调用以槽（alive，64 页约 702 MiB）或段（prefix，5 页约 55 MiB）为基址，行索引 = 槽内页 × (L × B) + 层 × B + 页内 token，行宽仍是 r，单次跨度 < 4 GiB、不改拷贝内核；验证不通过才最小扩展为 64 位偏移的读写路径，范围只限偏移算术。不能把约 11 MiB 的整页伪装成一条 token 行；也不在本票做票 11 的线程与批量执行器。
2. 布局层（`layout.py` 的 KVLayout / PoolLayout、`config.py` 的 make_mla_layout）：page first 地址与页跨度；B 由布局持有，各调用点不各写一套页内公式；集中提供三类能力：(层, 槽 / 页, token) → 设备拷贝用的行位置或地址；物理页 → 供池库用的整页字节地址与长度（页块接口）；布局类型、B、各维度序列化进签名。区域容量与探针隔离保留。
3. 会话与视图（`sharing_plan.py` 的 PoolSession.regions、`manager.py` 的 view / MempoolKVView）：按实际 5 页段构造 page first 几何，32 参与者与零贡献成员保留；视图支持页 / 层定位，逻辑层形状与物理连续范围分开，去掉“单层连续平面”假设；gva（池库地址）与 device（设备可访问地址）仍分开，共享映射地址不当普通 CPU 指针读。
4. 写回与稀疏读（`offload.py` 的 write、`copy.py` 的 SparseKVCopy / KVFetch、`runtime.py` 的 write_layer / fetch_selected_kv、`decode_write.py`）：目标 / 源物理行按新公式；mask、P 按页分写、Index K 写者配置、D 特征分写、prompt / decode 两源选择、当前 token 本地供给、请求绑定、ready 计数都不改。token 位置 → 行索引的变换在设备上对现有稳定索引缓冲逐元素做（槽基址也来自稳定设备缓冲），进图捕获；不新增每步主机读回或同步。
5. prefix 三操作（`prefix.py` 的 _submit / _submit_fill / _copy_region / _submit_load_back）：选页、分片、页归属复用 07 / 08，只换源 / 目标寻址；fill、admit 仍用逐层索引拷贝；load_back 保留逐层读取与两块汇总缓冲，`restore_kernel.py` 的 scatter_rows 复用（page first 不会把 load_back 变成对原生缓冲的整页 memcpy，原生目标页可以不连续）。`prefix_layout.py`、`split_read.py`、`page_write.py` 的逻辑布局与存储排列独立，预计只回归。
6. 注册与协议（`mempool_subrouter.py` 及注册入口、`mempool_router.py`、`mempool_accounting.py`）：传递布局事实；控制协议与完成语义（提交成功 ≠ 目标可读、按 op_id 轮询、admit 的 publish 链、fill 进 prompt ready 汇总、全 rank 汇总次序）不变；模型 attention 适配入口的 hook 时序不变，改动集中在专用适配层。若发现必须改通用主线文件，先说明文件、原因与行为影响。

**不变**：副本数 8 / 8 / 1 / 1 / 1、页归属与分片分工（07、08）、prefix 分配规则与描述符编码、alive 整槽后端（无散页、无动态 grant）、串行、三条件门控、结束顺序与 free_ack、HBM 原生布局、main router 的消息 / 页表 / 账本。不做：远端 prefix、动态分配、真实并发、按层流水、在线迁移、执行器线程与批量接口（票 11）、性能埋点恢复。

**验收与证据**（沿用 08 批准的证据边界：计算时的源快照、正常 load_back 后的设备数据、写读记录；不新增直接主存读回；物理 NUMA 驻留、性能、直接主存内容比较不在本票）

- 几何与寻址（CPU）：跨层、跨页（127 / 128）、跨槽、最后槽、跨段；两类数据；区域与探针不重叠；页块接口与行公式一致（任一页的所有行落在该页块内、相邻页块首尾相接）。
