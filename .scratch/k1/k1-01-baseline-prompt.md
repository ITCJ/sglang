> 用法：这是交给实施侧的目标 prompt。背景是阶段 0 已实现并验收（V1–V10 通过），下一阶段 K1 把主存副本从 16 / 16 / 16 / 16 改为 8 / 1 / 1 / 1。本票在 K1 动手之前完成。

## 0 目的与边界

- 目的：建立一个可重复的计时入口，并产出阶段 0 的基线报告。基线用于发现 K1 各票的性能回退，不用于证明收益；K1 的目标是容量。
- 本票只测量、只报告，不做调优，不改默认配置，不改 K1 相关代码。
- 已有的唯一数据点：128 输入、48 输出的功能检查，D 后端 `e2e_latency ≈ 11.12 s`，没有拆分。本票要回答这 11 秒由哪几段构成。
- 指标按事件语义定义，不绑定阶段 0 的实现细节。K1 换了读写路径之后，同一入口要能不改地跑出同一张表。

## 1 交付物

1. 验收入口的 perf 子模式：每台机器一条命令，自动完成启动、等就绪、预热、重复轮次、发请求、收日志、算统计、出报告、清理进程；失败返回非零。K1 的票 02–05 原样复用它。
2. 基线报告（markdown）：版本 / 配置 / 拓扑快照、指标主表、e2e 拆分、固定等待的发现、已知混淆项。
3. 原始样本（jsonl 或 csv）和各进程的结构化日志，与验收日志一起归档。
4. 报告生成器是对归档日志的离线脚本，可以重跑。

## 2 固定条件（与阶段 0 验收配置完全一致）

| 项 | 取值 |
|---|---|
| 模型与并行 | GLM-5.2；P、D 各一台 16 卡，各一个 TP 16 实例；attention TP 16、DP 1 |
| 页与槽 | 页 128 token；S_P = 8192（64 页）、S_D = 128（1 页）；prefix 每份 40 页 |
| 副本 | 16 / 16 / 16 / 16（阶段 0 现状）；layer-first |
| 运行方式 | 串行、单 chunk、非流式；计算图与验收相同（Graph 补齐的 batch 大小照旧）；deterministic 开关与验收相同 |
| 采样 | greedy；`ignore_eos = true`；`max_new_tokens = 128`；清除 stop 字符串 / stop regex；不加 min_new_tokens |
| 输入 | 与验收相同的 token ids：A 冷 4096；B = A + 1024 新 token，命中 4096；C = A，命中 3968；E 另一条冷 4096 |
| 有效样本 | 每条样本实际输出恰好 128 个 token 且按 length 结束；不满足的样本标为无效、不入统计，报告列出无效样本数 |

## 3 轮次与预热

- 一轮 = A → B → C → E，顺序固定：B、C 的命中由同一轮的 A 准备；E 在 prefix 满时跳过保存。预期每轮 prefix 占用 0 → 32 → 40 → 40 → 40，和 V6 一致。
- 跑 5 轮。第 1 轮为预热：保留原始样本、不入统计。每个指标的有效样本 ≥ 4。
- 轮与轮之间 prefix 必须回到空。默认做法：整套服务重启，入口已有启动和清理。若重启太慢，可加一个测试专用的 prefix 清空操作：main router 清目录、SR 释放全部 prefix 页；只在无请求在途时允许；写事件日志。报告写明用的是哪种。

## 4 指标与观察点

规则：每个指标只用一个进程的单调时钟；跨机器的区间只能用 main router 自己收到消息的时刻来算；不同机器的墙钟不相减。事件名沿用现有结构化日志。

**4.1 main router 时钟（每个请求）**

| 指标 | 起点 → 终点 | 用例 | K1 哪张票会改它 |
|---|---|---|---|
| T_main_e2e | 收到客户端请求 → 完整响应发出 | 全部 | 总包络 |
| T_route | 收到请求 → dispatch 发出（含入口检查、match_prefix、reserve、alloc 往返） | 全部 | 02 |
| T_op2 load_back | op 下发 → ack | B、C | 03、04 |
| T_op1 fill | op 下发 → ack | B、C | 02、03 |
| T_ready | dispatch 发出 → 收到 ready_tokens = prompt_len（B、C 含 fill） | 全部 | 02 |
| T_gen | ready → 收到 finished | 全部 | 02 |
| T_op3 admit | 收到 finished → 最后一个 publish 完成（C、E 为跳过或零页，也记） | 全部 | 03 |
| T_tail | 收到 finished → 最后一个 free_ack | 全部 | 02 |
| T_free_P、T_free_D | free 下发 → free_ack | 全部 | 02 |

**4.2 P 侧（每个 rank 用自己的时钟；汇总时报 16 个 rank 的最大值和最小值）**

| 指标 | 起点 → 终点 | 用例 | K1 哪张票会改它 |
|---|---|---|---|
| T_lb_rank | 本 rank 的 load_back 开始 → 本 rank 计算侧缓存恢复完成 | B、C | 03、04。按"本 rank 恢复完成"定义，K1 改成广播后仍成立 |
| T_prefill | 本请求 forward 开始 → forward 结束（只含新算段） | 全部 | 不改，作参照 |
| T_wt_rank | forward 开始 → 本 rank 新算段的主 KV 与 Index K 写回完成 | 全部 | 02 |
| T_send | Index K 发送与 handoff 完成 | 全部 | 不改，作参照 |
| T_hbm_release | forward 结束 → 本 rank 释放 HBM | 全部 | 不改，V5 已有 |

**4.3 D 侧（D rank 0 的时钟）**

| 指标 | 起点 → 终点 | 用例 | K1 哪张票会改它 |
|---|---|---|---|
| T_gate | 收到 dispatch → 三条件齐；prompt ready、Index K ready、handoff ready 的到达时刻分别记 | 全部 | 02 |
| T_first | 收到 dispatch → 首 token 发出 | 全部 | 02–04 合计 |
| T_step[i] | 第 i 步 decode 开始 → 结束；预期 127 步（首 token 来自 P 的 prefill），以实际步数为准；报 p50 / p90 / p99 / max，第 1 步单列 | 全部 | 02 |
| T_finish | 最后一步结束 → finished 发出（含 HBM 与原生槽位清理） | 全部 | 02 |
| 后端 e2e_latency | D 后端已有的数 | 全部 | 包络 |

可选：每步从 P alive、D alive 各读了多少字节，若现有读路径能便宜地记。不是必做。

**4.4 不测、不作替代**

- 客户端口径的 TTFT、ITL：接口非流式，没有这个观察点。
- 批次刷新、直方图一类的汇总统计：不能替代逐步原始样本。
- 长生成：S_D 保持 128，长生成留给 L1。
- 并发、故障注入、超时注入、profiler 采集：都不进计时轮次。

## 5 计时轮次里的正确性检查

- 保留轻量断言，保证计时的样本是正确的样本：V1 命中长度（B 4096、C 3968）；V3 输出 token 序列与各自的参考一致；V6 账本等式与 prefix 32 → 40 → 40 → 40；每条样本 128 个 token 且按 length 结束。
- 关闭重型检查：V2 的 HBM → host 逐 token 比对、V4 的复制适配器用例，不在计时轮次里跑。
- 失败处理：某样本断言失败 → 该样本无效，本轮后续用例作废，重启进入下一轮；报告列出。有效样本不足 4 个则入口返回非零。

## 6 拓扑与版本快照（随报告归档）

- mempool 代码 commit、sglang commit、驱动与 CUDA 版本、拷贝实现版本。
- `nvidia-smi topo -m`、NUMA 数、每份副本实际落在哪个 NUMA（P、D 各 16 份，按注册上报的 rank → NUMA 映射）、P ↔ D 的网卡与是否 GPUDirect RDMA。`../mempool-design/copy-perf-tests.md` 第 6 节的清单可直接套用。
- NUMA 映射两跑：若阶段 0 能按显式 rank → NUMA 映射启动，则整套 5 轮跑两次：一次现有配置；一次 K1 目标映射（用全部 8 个 NUMA，每个 NUMA 放两个 rank 的副本）。两张表并列。若不能，跑一次，并在报告里把"K1 将改变 NUMA 用法"列为已知混淆项。

## 7 统计与报告格式

- 每个指标 × 用例：n、p50、min、max；T_step 另加 p90、p99。
- 原始样本字段：round、case、rid、metric、value_ms、clock（进程与主机）、valid。
- "阶段 0 基线"主表：固定列。K1 各票用同一入口原样复现这张表。
- e2e 拆分：A 和 B 各一张：T_main_e2e = T_route + T_ready + T_gen + T_tail + 残差；残差要能解释（消息往返、main router 自身处理）。
- 固定等待的发现：若某段含空转等待（轮询间隔、sleep、逐条 ack 往返），点名位置并估算占比。只报告与建议，不在本票修改。
- 稳定性：某段跨有效轮的 max ÷ min > 1.5 → 加轮次或解释原因。
- 已知混淆项：非流式、Graph 补齐 batch、串行、单 chunk、NUMA 映射。

## 8 实现提示

- 现有结构化日志（route / alloc / ack / publish / finished / free_ack，带时间戳、rid、op_id、槽号）已覆盖 4.1 的大部分。缺的是：D 每步的开始与结束时间戳；P 每个 rank 的写回完成与恢复完成事件；D 三条件各自的到达时刻。
- 每条事件带进程名、主机、单调时钟。
- perf 子模式用开关关闭重型检查；验收模式不变。

## 9 完成标准

1. 每台机器一条命令跑完 perf 子模式，产出报告、原始样本、日志归档；失败返回非零。
2. 报告含第 6、7 节的全部内容；每个指标 ≥ 4 个有效样本；A、B 的 e2e 拆分和固定等待的结论。
3. 计时样本全部通过第 5 节的轻量断言。
4. 用户在真实环境运行并核对后，本票关闭；随后 K1 票 02 的验收以这张表为对照。
