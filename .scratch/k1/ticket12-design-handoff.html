B

当前存储、分配与映射

B1 已经实现的共享布局

配置为 P/D 各一台主机、每侧 TP16、attention TP16、DP1。 当前模型主 KV 有 78 层、每 token 576 个 BF16 元素。 Index K 有 21 个生产层、每 token 128 个 BF16 元素。 这些是当前模型实例值，布局计算应从模型几何推导。 Index K 的 21 个局部层编号与模型层编号通过 producer 列表映射。

主机内存区域 物理副本数 owner 与分工
P alive 主 KV 8 组 {2k, 2k+1} 共享；owner 为 2k；组内按整页分写
D alive 主 KV 8 同样分组；默认按特征维分写每步新行，也支持按层分工
P alive Index K 1 NUMA0、owner rank0；默认只有 rank0 写，已有多写者配置
prefix 主 KV 1 一份完整数据分成 8 个 NUMA 段，各段 owner 为 2k
prefix Index K 1 与 prefix 主 KV 共享逻辑页归属、段和页描述符

五项副本数为 8 / 8 / 1 / 1 / 1。 D 生成的 Index K 仍留在设备内存，没有新增 D alive Index K 主存池。 底层共享池会话覆盖 P/D 共 32 个参与者。 物理副本、映射者、实际写者、会话参与者是四个不同概念。

所有执行 fill 的 P 分片需要访问全部 prefix 段。 admit owner 需要访问本组 alive 主 KV 和 NUMA0 的 alive Index K。 当前访问由设备侧索引拷贝完成，映射范围覆盖实际访问范围。 增加映射没有增加物理副本；不能沿用“只有 owner 有设备映射”的假设。

B2 页管理已经存在，存储排列仍是 layer-first

统一 token 页为 B=128，主机内存与原生设备页使用相同 B。 验收配置的 P/D alive 每份各有 16 个槽，S_P=8192、S_D=128。 alive 仍按整槽预留和归还；prefix 已有真正的按页空闲表。 当前只有一个真实请求在运行，16 个槽和图的补齐行不代表并发 16。

prefix 总容量为 40 页，8 段各 5 页。 物理页编号编码为 segment × 5 + local_page，Main 只转发描述符。 每个请求记录一次起始段，分配按段轮转；段满时选剩余页最多的段。

A 保存 32 页后，各段有 4 页；B 再保存 8 页后，各段有 5 页。 这些分配规则与 page-first 是独立的，12 可以原样保留。

当前主存区域的紧凑布局为：

alive:      [layer, slot, token_in_slot, head, feature]
prefix段:   [layer, local_page, token_in_page, head, feature]

区域内部目前先放完整的第 0 层，再放完整的第 1 层。 单页跨层数据不连续；跨 NUMA 的交错选页也没有改变这个事实。 段内 prefix 每层 stride 按 5 页计算，不是按总容量 40 页计算。

对于区域基址 R、每 token 行宽 r、每层大小 layer_bytes：

alive地址 = R + layer × layer_bytes + (slot × S + token) × r
prefix地址 = 段内区域基址 + layer × 段内layer_bytes
             + (local_page × B + token_in_page) × r

区域数据量由各维度乘积决定，主 KV 与 Index K 是两个独立区域。 池的实际贡献还包括探针区和库要求的对齐，不能只看有效数据字节。 08 报告的库分配贡献为 P 合计 96 GiB、D 合计 8 GiB。 这不等于物理 NUMA 驻留已经验证；验收源快照的内存另计。

C

现在的读写调用链与完成语义

C1 P 写回与 D 读取

P 每层得到主 KV 后，拼成 576 维连续行，写入该请求的 alive 槽。 共享组成员按完整 prompt 的页范围分工；命中长度不改变写者归属。 有 prefix 命中时，模型只计算后缀，命中段由 fill 写入 alive。 Index K 在生产层从原生设备缓冲取值，按其独立写者配置写回。

D 的稀疏 miss 读取按 token 位置选择源：

  • 小于 prompt 长度：读取绑定的 P alive 槽。
  • 属于已物化生成段：读取绑定的 D alive 槽。
  • 当前步的新 token：先由本 rank 的设备缓冲供给。

P 槽和 D 槽可不同。D 主存中的位置是生成段相对位置。 padding、无效请求行和未写位置继续由既有 mask 排除。 这些逻辑选择应保留，只把最终物理寻址适配为 page-first。

D 默认按特征维分写新行，写回在计算流上执行。 现有实现利用后续全员 TP 通信保障后一步可读，不新增跨进程握手。 当前 token 的本地供给解决本步还未合齐的问题。 12 必须保留该顺序与特征切分，不能把部分 token 更新变成整页覆盖。

C2 三种 prefix 操作

操作 当前数据路径与分工 完成依据
op2 load_back 每个读者只读取分到的页；逐层读入本 rank 的汇总缓冲切片，all_gather 后恢复原生设备页 读取、集合通信和原生 scatter 全部完成
op1 fill 每组从全部 prefix 段直接填自己的 alive 主 KV；组内按页分工；Index K 只填单份 本分片的设备完成事件，再由 SR 汇总
op3 admit 8 个 owner 各保存本段页；主 KV 源为本组 alive，Index K 源为单份区域 设备事件完成、SR 核对单写者覆盖并汇总，然后发布

load_back 的读者按页的实际 NUMA 段分配。 组 k 的两个 rank 平分段 k 的命中页；零页读者仍参加集合通信。 主 KV 和 Index K 各复用一块汇总缓冲，逐层复用。

每次恢复只建一张“汇总槽位 → 原生设备行”的表，两类数据共用。 主 KV 恢复时拆回 512 维与 64 维两个原生缓冲。 Index K 按 producer 层映射恢复到各自原生缓冲。

原生目标页可以不连续；通信 padding 不产生额外主存读取。 31 页命中时各段真实读取量不相等，这不是错误。 page-first 不会自动把 load_back 变成对原生缓冲的一次整页 memcpy。

当前 fill/load_back 由 PrefixStore._read_context() 使用独立设备流。 它们仍由 worker 的有序执行路径提交，没有 11 要求的独立主机执行器线程。 admit 在其调用流上提交；三类操作均使用事件查询完成。 池间 copy 目前仍逐层调用按 token 行索引的拷贝接口。 它是批量行索引，不是 Python 每 token 调用一次。

C3 控制流与所有权

Main 负责匹配、逻辑分配、源保护、发布、额度和串行准入。 SR 仍嵌在 worker 内，rank0 协调、各 rank 执行分片任务。 网络线程只入队，集合通信仍在有序调度 tick 中发起。 Main 持有不透明页描述符，具体地址由持有映射的分片解析。

“提交成功”不是“目标可读”。 操作按 op_id 提交一次，后续 tick 轮询同一操作。 对 admit，完成汇总后才能发布，再释放源，收到 free_ack 后恢复额度。 fill 的完成进入 prompt ready 汇总，不应给它套用 admit 的 publish 阶段。 零工作分片可以不搬数据，但仍须遵守原有全 rank 汇总次序。

D 启动仍等待 prompt ready、Index K 到达和 handoff 三条件。 finished、原生资源释放、共享源释放和 free_ack 继续分开处理。 fail-stop 时保留未确认资源；最终进程清理由原有父进程路径完成。

D

page-first 的建议范围与具体改造点

以下是交给你定稿的代码方案，尚未实施。

D1 建议一次转换全部五类主存区域

建议 12 同时转换 P/D alive 主 KV、P alive Index K、两类 prefix。 只改 prefix 会让 fill/admit 继续承担布局转换，11 仍不能直接搬整页。 设备端原生 KV、Index K 和 attention 缓冲继续沿用原生格式。

建议页内采用 [layer, token_in_page, head, feature]。 alive 暂时用 [slot, page_in_slot, layer, token_in_page, head, feature]。 prefix 每段使用 [local_page, layer, token_in_page, head, feature]。 两类数据继续分区保存，同一个逻辑页分别对应两个连续块。

令 L 为该区域层数、r 为该区域 token 行宽：

alive_physical_page = slot × (S / B) + floor(token / B)
prefix_physical_page = local_page
in_page = token % B
page_bytes = L × B × r

地址 = 对应区域基址 + physical_page × page_bytes
       + layer × B × r + in_page × r + 行内字节偏移

这是建议公式，不是当前 byte_offset() 的实现。 该方案改变物理排列，不要求引入 alive 散页分配器。 alive 的页归属仍由槽位换算；真正的动态页分配保留在后续阶段。 建议以服务重启重建临时池，不在本票加入在线旧数据迁移。

D2 最小接口接缝

建议在现有布局和 view 层集中提供三类能力：

  1. 给定层、槽/页、token 位置，得到设备拷贝需要的行位置或地址。
  2. 给定物理页，得到供池库使用的整页字节地址与长度。
  3. 序列化布局类型、B 和各维度，复用已有启动一致性检查。

以上是接口职责，不预先指定新类层级。 当前 KVLayout 没有布局类型或 page_size 字段，B 来自上层配置。 设计时应明确 B 由谁持有，避免多个调用点各写一套页内公式。 当前 MempoolKVView 的“单层连续平面”假设需要改变。 page-first 的同一层跨页有间隙，不能只替换 device_base 而保留线性行号。

gva_base 对应池库地址；device_base 对应设备可访问地址。 这两类地址已有区分，应保留，不能当作同一种裸指针。 共享映射的地址也不应直接当普通 CPU 指针读取。 现有实机排查已经否定过这种直接读法。

D4 需要先解决的真实接口限制

当前索引拷贝的布局检查限定：单行最多 32 KiB，单层跨度不超过 UINT32_MAX。 现在 P 每层只有 144 MiB，而完整 P 主 KV 区域约为 10.96875 GiB。 旧接口通过层基址隔离跨度；page-first 的跨页索引可能跨过 4 GiB。 仅修改 Python 索引公式，不足以证明底层访问安全。

建议先在小范围验证以下方案之一，再选最小可行实现：

  • 现有拷贝接口能安全接受新物理跨度，就复用并补齐边界证据。
  • 若不能，就采用明确的分段基址，或最小扩展为支持页表/宽地址的读取写入路径。

当前尚未验证哪种方案可用；不能预先承诺“完全不改底层拷贝”。 此适配属于 12 的布局正确性，不等于提前实施 11 的线程与批量执行器。 也不能把约 11 MiB 的整页伪装成现有接口的一条 token 行。

图捕获/重放同样必须覆盖新地址计算。 动态绑定与 token 位置继续用稳定的设备缓冲，不能引入每步主机读回。 零有效行、补齐行和换槽后的重放仍须保留正确的访问路径。

E

12 与 11 的分界及新清单公式

建议 12 的完成点是：全部主存区域已为 page-first，现有服务路径能正确运行。 12 可以继续使用现有逐层索引拷贝，只把物理寻址改正确。 12 同时给出可核对的整页连续块接口，供 11 接入。 这样 12 单独验证布局，11 单独验证异步执行与完成回报。

11 再把 op1/op3 接入池库批量接口和每分片执行器。 每次提交包含两类数据；等待或查询真实完成后，再回报目标可读。 旧设备事件不能直接证明库内部传输队列已完成，11 必须定义对应完成桥接。

本地库源码已有连续块批量提交、异步标记和释放 GIL 的包装。 这只是源码依据；实际可用性和完成语义仍需在 11 的实机路径验证。

12 不承诺性能收益，11 也不能把段数减少当作性能已经改善。 load_back、写回、稀疏读取均因 12 适配新布局；11 仍只更换 op1/op3。

E1 每页有效字节

按当前模型、B=128、紧凑无额外页内 padding：

M = 78 × 128 × 576 × 2 = 11,501,568 bytes  // 主 KV 一页
I = 21 × 128 × 128 × 2 =    688,128 bytes  // Index K 一页
M + I = 12,189,696 bytes

page-first 让主 KV 的 78 个层片段变为一个整页块。 Index K 的 21 个层片段也变为一个整页块。 但全系统清单条目数还取决于物理目标副本数量。

E2 必须分别核算 admit 与 fill

下表按所有实际搬运分片求和，统计合并连续条目前的页块条目。 N 在 admit 中是新保存页数，在 fill 中是命中页数。

操作 物理目标 layer-first 规范化片段数 page-first 规范化片段数 实际载荷字节
admit 1 份主 KV + 1 份 Index K N × (78+21) 2N N × (M+I)
fill 8 份主 KV + 1 份 Index K N × (8×78+21) 9N N × (8M+I)

这是数据范围的规范化计数，不是当前逐层算子的调用次数。 批量接口还可能合并源、目标都连续的相邻页，实际提交条目可以更少。 应分别记录页块清单条数、合并后条数、总字节和覆盖范围。

32 页 admit：3168 个层片段可变为 64 个页块。 32 页 fill：20640 个层片段可变为 288 个页块。 不能把旧票的“全分片 N×99”统一替换成“全分片 N×2”。

load_back 从主存读取的总载荷仍为 N×(M+I)。 all_gather 的通信 padding 和传输量不属于主存实际读取字节。 它的逐层恢复粒度建议在 12 保留，不强制变成两次整页读。

F
