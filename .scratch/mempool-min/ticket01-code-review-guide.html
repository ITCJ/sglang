本票实现了哪条路径

Main 保存配额账本、页目录、操作编号和请求阶段。 各侧 rank 0 协调 SR，每个 TP worker 持有一个分片。 分片执行实际分配，返回不透明的页描述符。 Main 不保存设备地址，也不替 worker 选择物理页号。

四处共享主线改动为何必要

这四处累计新增 29 行、删除 4 行。 预留策略和状态都在 Ascend 模块；主线提供调用点。 原生检查、分配和请求字段修改发生在这些函数内部。 仅在 Ascend 模块新增方法，不能改变主线调用顺序。

顺序与文件 实际改动 必要性及调用点为何在主线
13 disaggregation/prefill.py 把已有 service.track(req) 从 add 尾部移到 create_sender 中、_process_req 前。 _process_req 会把 max_new_tokens 改成 1。SR 必须在修改前核对 Main 原始生成预算，否则合法 dispatch 会不匹配。原调用时机由此主线函数决定。
14 disaggregation/decode.py 增加 alloc_rows/free_rows；已预留请求跳过重复的空闲容量检查；pre_alloc 通过 attach 接入已有 row/indices。 SR 分配时还没有原生 Req。请求到达后需要复用预留，避免二次分配或因已占用资源被误拒绝。原生行池、入队检查和 pre_alloc 入口都在此文件。
15 managers/schedule_batch.py check_decode_mem 调用 reservations.can_decode。 资源已提前扣除，全局 free pages 不代表本请求是否还能 decode。该容量判断在进入实际分配前执行，需要此处检查预留剩余量。
16 mem_cache/allocation.py alloc_for_decode 返回 reservations.decode 的下一段预留 indices。 实际每步 out_cache_loc 在此产生。这里必须消费已有预留，避免再次从全局 allocator 分配。具体索引和长度更新仍由 Ascend 类实现。

非 Router 路径继续执行原逻辑。 Router 模式下，applies_to 只允许明确的 fake warmup 走原生分配路径。 真实请求缺少预留仍报错，fake 与真实请求混批也会被拒绝。
