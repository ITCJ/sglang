## 拆分理由与共通交付条件

- 保持用户确认的首片边界。01 包含 Main Router、SR 和真实服务闭环；单独的
  schema、账本或空 Router 框架不作为一个可交付切片。
- 02 将 P alive Index K 写回与 cold prefix 保存放在一起。P 原生 HBM 可以提前
  释放，保存不能依赖 D 结束后再从 P HBM 补取 Index K。
- 03 将部分命中与完全命中放在一起。它们共用恢复、原生 allocator 接续、suffix
  进度和完成条件；3968-token 完整页命中边界是同一行为必须覆盖的输入。
- 04 交付可独立运行的完整验收流程，贯通跨请求场景与报告。01–03 各自必须已经
  有测试和自运行入口，不将数据正确性、释放条件或 fail-stop 延到 04 才实现。
- 目前未发现需要独立成票的广泛重构。01 内先整理旧控制副作用与显式资源操作的
  边界，再接入新链路；保持既有设备读写和必要身份校验。其余局部调整随所属行为
  一起交付，不增加通用多模式框架。
- 每票使用同一份规格约束：Ascend NPU、GLM-5.2、P/D 各 TP16、attention DP1、BF16、串行、
  单 chunk、私有副本、S_P = 8192、S_D = 128、生成上限 128。完整 prefix 功能
  使用每份 40 个逻辑页（5120/B）、严格相同的 B-token DRAM／原生 HBM 页（当前 B=128）。
- 每票包含 CPU 行为检查、相应 NPU 验收入口、中文路径／所有权／同步说明和
  实际执行记录。用户运行硬件测试；未验收项保留，不能用 mock 或历史报告代替。
- 双机测试允许每机一条命令，自动完成后续协调、就绪、请求、断言、报告和自身
  进程清理。日志写入 `/home/cryang/log/`，失败返回非零，smoke 与完整验收分开。
- 01 的入口负责拉起 Main、P、D，SR 随 worker 加载；BM 映射先于 Graph，控制
  握手及完整注册后才接收请求。02／03 扩展同一入口，不另起一套启动链。
- 每次实现后立即更新[目标页 D](target-alignment.md)，同步 HTML，记录代码、
  CPU 检查、待执行项与用户 NPU 验收。阶段 0 完成不删除整个 demo 的临时跟踪规则。
- 01–03 在各自功能变化后运行必要检查；04 在最终集成版本执行完整场景，不要求
  每次文档或无关变化都重复全部硬件测试。
