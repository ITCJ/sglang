A

统一约束与交付状态

DRAM 逻辑页与原生 HBM 页严格共用可配置的 page_size=B。 sparse、dense、P/D、alive/prefix、Index K 相关池都遵守此约束。 整数倍关系不能代替相等。本次决定取代旧 sparse 64/128 约定。

当前 GLM-5.2 mempool-min 集成默认并仅允许 B=128。 SUPPORTED_PAGE_SIZES=(128,) 是此集成的开放范围，不是全部 Ascend 硬件的能力表。 后端默认值见 hardware_backend/npu/utils.py；实际池、allocator 和传输布局也须相等。 其他值须完成对应后端、池与 kernel 的能力验证后再开放。

dense 的设计、检查点及跟踪间隔已统一；dense 服务集成仍属于后续工作。

开始时核对分支 cryang/dev/mempool-min，HEAD 为 af517b1a23a115d19fddd639e249c73e44a7614f。 原有未提交工作保留。本次以会话开始时的文件快照统计，共修改或新增仓库内 37 个文件、设计源 17 个文件。 仓库内包含 5 个功能文件、3 个启动/验收脚本、6 个测试文件、21 个说明及图解文件和 2 个验证证据文件。

本次没有新增公共主线功能改动。原 ticket01 已有的公共接缝继续使用实际 allocator 页大小。 两次 UniDexCopy 的 sparse fetch 按 token 索引搬运，调用链未发现页粒度冲突。 OS 内存页、BM 字节对齐、64 字节探针、512/64 特征维、kernel chunk 和 Graph padding 均另有含义。

B

旧公式与新公式

以下数值例统一取 B=128。L 是 prompt token 数，G 是生成预留上限。 最小 demo 的输入及整槽容量必须按 B 对齐；完整设计另保留尾页场景。

项目 旧口径 新公式与本例
DRAM / HBM token 页 64 / 128 同一个 B / B
hash、目录页与输入边界 按 64 分块 按 B 分块；完整页数 L/B
4096-token prompt 64 个逻辑页 4096/B = 32 页
5120-token prompt 80 个逻辑页 5120/B = 40 页
相同完整 prompt 的命中上限 4032，最后 64 token B×floor((L−1)/B)；4096 时为 3968，重算最后 128
prefix 容量 80×64 = 5120 token (5120/B)×B；本例 40×128，容量不变
A/B/C/E 后 prefix 占用 64→80→80→80 页 32→40→40→40 页；E 仍遇到 prefix 已满
P alive 整槽 8192/64 = 128 页 S_P/B = 64 页；有效 prompt 仅前 32 页
D alive 整槽 128/64 = 2 页 S_D/B = 1 页
16 槽 P/D 账本 2048 / 32 页 16×S_P/B = 1024；16×S_D/B = 16
slot s 的逻辑页 s×(capacity/64)+i s×(capacity/B)+i
native 预留 HBM 独立按 128 算 ceil((L+G)/B)；4096+128 仍为 33 页，5120+128 为 41 页
byte 预算 单页 token 数单独硬编码 页数×B×每 token 字节×层数×物理副本数
Index K 单页 单独的 HBM 边界 B×256 字节/producer 层；主 KV 的特征维不随 B 改
dense 状态 128-token 检查点 B-token 检查点与跟踪间隔；kernel 内部 chunk 独立

小例仍用 256/384-token prompt、512-token P 槽、128-token D 槽。 prefix 保持 384 token，改为 3 页；A/B 有效页为 2/3，C 命中 128 后重算 128。 完整设计保留 8200-token 尾页例：65 个 prompt 页，尾页已有 8 token。 生成预留 512 时，DRAM 生成区需 5 页，native 总计 69 页，其中新增 4 页。

旧“4032 命中、HBM 半页接续”已撤出当前验收。 提前 EOS、实际尾页、未用整页与未用预留仍须正确清理。 native 释放保存的完整索引集合，发生在 drain 之后，并且只释放一次。
