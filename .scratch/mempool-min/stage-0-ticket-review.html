B

Main Router、SR 和 scheduler 怎样分工

Main Router 是独立 CPU Python 进程，拟默认部署在 P 机。 SR_P、SR_D 随两侧推理进程加载。 每侧 rank 0 scheduler 放置一个 SR 协调者。 每个 rank 都有 SR 执行分片，包括 rank 0。 因此每侧是 1 个协调者加 16 个分片；分片无需单独启动进程。

最后一条边表示保留的 P_i/D_i 原生通道。 实际传输由已有推理与传输模块完成。

角色 负责决定或执行什么 不应混淆的边界
Main Router 入口检查、跨侧配额、目录、命中、操作编排和源保护 保存不透明描述符，不计算设备地址
SR 协调者 选择本侧槽或 prefix 页、下发一致操作、汇总全部 rank 完成 本侧一个 rank 完成不足以回成功 ack
SR 分片 校验本地绑定、解析映射、执行复制、检查设备完成和归还 分片是执行职责，不代表只存 1/16 的主 KV
Scheduler 接收原生请求、推进队列、选择 batch、调用 forward、处理结果 每个 rank 都有；rank 0 额外承载协调职责
ModelWorker / NPU runtime 执行本 rank 的模型计算与实际设备读写 提交成功与目标已经可读分开判断

例子：A 有 4096 个 prompt token，所有槽都空闲。

  1. Main 预留额度，向 SR_P 发 alloc(A)。
  2. 协调者选择 slot 0，并下发到 16 个分片。
  3. 各分片占用本地槽，返回描述符。
  4. 协调者收齐成功结果，才回 alloc_ack。
  5. dispatch 后，各 scheduler 驱动共同的 prefill。
  6. 各分片报告本 rank 的实际写回完成。
  7. 若 rank 7 未完成，协调者继续等待。
  8. 全部完成后，协调者才报告 prompt ready。

rank 0 自己也有分片，其结果同样需要汇总。 阶段 0 的 16 份主 KV 都覆盖完整逻辑内容。 这与 TP 模型计算如何分工是不同的维度。

现有 scheduler.ingest_requests 已调用 mempool_service.advance。 SR 将沿这个有序 tick 接入。 网络线程只收发并入队；allocator 和 TP 通信在约定的 tick 位置推进。 空闲 tick 也要处理控制消息，避免等待时没人推进。 tick 返回不表示 NPU 工作已经完成。

通信的拟定落地方式是 HTTP 加 ZMQ。 Main 对外收 token IDs，经 ZMQ 与协调者交换控制消息。 原生 HTTP 用于创建匹配 dispatch 的 Req，并保留输出路径。 直接访问后端 HTTP 也必须校验已获授权的绑定。 这些接口和模块名属于实施方案，尚未实现。

C

page、slot 和 NUMA 共享的准确关系

阶段 0 已有逻辑 page 接口，alive 暂时由整槽承载。 prefix 从 02 开始按 page 分配。 两者的分配粒度需要分别理解。

名称 阶段 0 的含义 示例
DRAM 逻辑 page B token；用于目录、页表和命中 B=128 时 4096 token 为 32 页
alive 存储 slot 一个请求独占的连续区域 P 每槽 8192 token，即 64 页额度
HBM page 原生 allocator 管理；本次验收为 128 token 3968 token 占用 31 个完整页
req_pool_idx 原生请求行编号 与 P/D mempool slot 分别分配

P 池内逻辑页号为 slot × (8192 / B) + 槽内页号。 P slot 0 覆盖页 0–63；slot 1 覆盖页 64–127。 A 只在 slot 0 的页 0–63 写入有效 prompt。 页 32–63 仍被这个请求占用，不能借给别的请求。 因此账本扣除 64 页额度，不能只扣 32 页。

“最小空闲 slot”就是选择编号最小的空闲槽。 全空时选 0；0 占用而 1 空闲时选 1。 归还 slot 0 后，下一次可以再次选 0。 这个规则使槽位复用可以通过 alloc/free_ack 直接核对。

P、D 分别选择自己的最小空闲槽，编号允许不同。 D 的槽只放生成段主 KV。 若 prompt 长度为 4096，全局位置 4096 对应 D 槽内偏移 0。 全局位置 4097 对应偏移 1，须实际经过 forward 才有相应 KV。 刚采样但未经过 forward 的最后一个 token 尚无 KV。

同一个 NUMA 节点与同一份物理 KV 分开判断。

场景 rank 0 的 page 7 rank 1 的 page 7
阶段 0：两 rank 分配在同一 NUMA 私有副本中的逻辑页 7 另一份私有副本中的逻辑页 7
后续共享接入：同一共享组 同一份物理主 KV 的页 7 映射这份相同物理内容，虚拟地址可不同

用户要求的“两 rank 共享 page 编号与内容”在后续共享接入实现。 该功能在原文称为 K1，安排在这四票验收之后。

数据种类 阶段 0 全功能 后续共享目标
alive 主 KV 每侧 16 份 每侧 8 份，每组 2 个 rank
P alive Index K DRAM 16 份 1 份
prefix 主 KV 16 份 1 份
prefix Index K 16 份 1 份

01 尚未启用后三类 DRAM 区域，注册时必须如实标记。 D 生成 Index K 在阶段 0 留在 HBM。 共享以后仍可保留每 rank 一个 SR 分片。 分片数量与物理副本数由不同配置描述。

旧 NUMA 共享 02 只覆盖共享接入的部分范围。 它还需要适配新 Main/SR，并补齐其余数据共享与广播。 当前 启动检查 仍拒绝生产 share=1。 共享组件实验通过不能替代真实模型服务接入。

page-first 布局安排在后续“远端 prefix 与布局调整”。 alive 真正的 page 分配器安排在“并发与动态容量”。 布局、分配粒度、物理共享是三项独立工作。

D

Ticket01：真实冷请求与显式释放复用

完成标准：新 Main/SR 链真正驱动两次 NPU 推理，并正确归还和复用资源。 本票不启用 prefix 或 P alive Index K DRAM。 已有 P 主 KV 写回、D 两侧读取、Index K 传输继续复用。 更细的拟定模块与协议见 ticket01 实施方案。

一次冷请求的路径

  1. 两侧注册实际布局、容量和 rank 集合。
  2. Main 检查输入与资源，再关闭串行门。
  3. Main 预留四类额度，SR 执行实际分配。
  4. 两侧安装请求身份与 P/D 页表绑定。
  5. 两侧 dispatch 确认后，创建原生 Req。
  6. P 计算 prompt，并真实写回主 KV。
  7. 原生通道传 Index K 和 handoff。
  8. D 等三条件齐备，再输出首 token 并 decode。
  9. D drain 与原生清理完成后，报告 finished。
  10. Main 下发 free，两侧实际归还再回 free_ack。
  11. 全部额度恢复后，才允许第二个请求进入。
预留资源 4096-token prompt、最多生成 128 时
P alive 1 个整槽；64 个逻辑页额度
D alive 1 个整槽；1 个逻辑页额度
D Index K HBM 每个必要 rank 实际预留 ceil(4224/128)=33 页
D 原生请求行 每个必要 rank 实际预留 1 行

Main 管容量账本，SR 负责实际分配结果。 16 个副本的容量不能相加，算成 16 倍可服务请求数。 P 原生 HBM 由静态 prompt 上限保证，另随原生生命周期清理。

01 最主要的三处实现工作

工作 需要做到什么 需要防止什么
D 原生预留 alloc 时取走真实行和页；decode 从预留范围消费 账面减 33 页，后续才向全局池临时申请
全 TP 就绪 Router ready、Index K、handoff 三条件全齐 rank 7 迟到时，其余 rank 提前进入 decode
显式释放 drain、native 清理、finished、free_ack 分离 原有 DONE 或 drain 绕过 Main 直接归还

预留适配还要处理提前 EOS、实际尾页和未使用整页的归还。 已交给原生清理的页与尚未消费的页不能重复 free。 预留容量也不能伪装成已经写入 KV 的长度。

已核对的旧行为位于 finish_drain 和 _accept_done。 新模式要接管它们，以及早到、迟到 DONE 和取消回滚的分支。 继续保留身份、绑定和设备读写安全校验。

三个完成事件各表示什么

事件 可以据此做什么 alive 是否可以复用
P native release P 原生 HBM 和请求行已清理 否；D 仍可能读 P alive
D finished D 最后读写及原生清理已完成；退还对应原生额度 尚不能；还要走显式 free
SR free_ack 对应 alive 已无依赖且实际归还 是；Main 才恢复整槽额度

01 的测试包含两个不同的 4096-token 冷请求。 完整输出与同长度的既有正式 mempool 冷算参考比较。 还要验证真实 decode、P/D 来源、Graph 和 padding 行。 CPU 侧覆盖迟到 rank、重复回执、拒绝、无 free 不复用等行为。 任何内部失败走 fail-stop，不在本轮强行回收后重试。 用户执行 NPU 验收并确认后，本票才关闭。

E

Ticket02：请求结束后保存 prompt 到 prefix

完成标准：P 原生 HBM 和请求 alive 都释放后，prefix 仍保留完整数据。 本票仍让请求冷算，关闭 match_prefix。 因此“保存正确”与“命中计算正确”可以分别验证。

本票增加三组能力：

能力 实现位置与职责
P alive Index K 每 rank 增加 21 层 × 16 槽 × 8192 token 的 DRAM 区域
prefix 页池 SR_P 按 B-token 页分配；每 rank 容量 40 页
目录与 admit Main 管 token 页哈希、父关系、状态、源保护和 publish

Index K 每 token 每 producer 层为 128 维 BF16，即 256 B。 主 KV 每 token 每层为 compact 576 维 BF16。 保存同时覆盖 78 层主 KV 和 21 个 Index K producer 层。 主 KV 与 Index K 都完成写回后，P 才能释放相关原生资源。 这样 D 结束后，admit 可以直接从 alive 取数。

A 冷请求结束后保存 32 页的步骤

  1. SR_D 报告 finished；Main 重新检查目录。
  2. 查出缺少 ready prefix 位置的 prompt 页。
  3. 按实际空闲页数确定保存范围。
  4. 先保护复制源和所需父路径。
  5. 再解除请求对 alive 的 owner hold。
  6. SR_P 分配 writing 目标，执行 admit 复制。
  7. 全部必要 rank 确认目标可读，才回 ack。
  8. Main 按父页先于子页的顺序 publish。
  9. 解除源保护，满足条件后 free alive。

例如 A 的源页起初只有 owner hold，lock_ref=1。 计划 admit 后增加源保护，lock_ref=2。 解除 owner hold 后仍为 1，源不能复用。 复制完成后解除最后一份保护，才具备回收条件。 重复 ack 对这次操作只能生效一次。

ack 证明目标已经可读；设备提交返回不足以确认保存。 复制只能使用映射实际支持的 CPU 或 NPU 接口。 不把 BM 设备地址直接当作可解引用的 CPU 指针。 完成收据按请求和操作独立保留，不能依附已释放的原生请求行。

容量、去重和失败行为

情况 行为
A：首次 4096 token 保存 32 页，每份 prefix 占用 32/40
B：A 加 1024 新 token，仍冷算 跳过已有 32 页，只增加 8 页，达到 40/40
C：与 A 相同，仍冷算 已有 ready 内容全部跳过，仍为 40/40
E：不同的 4096 token prefix 已满，跳过保存，仍正常结束并释放 alive
仅剩部分容量 从尾部缩短保存范围，保留可发布的连续前缀
复制失败或超时 fail-stop；保留受保护源和 writing 目标，结束本轮

上述 A/B/C/E 是 02 的冷算保存变体。 它们不证明 03 所要求的命中长度或后缀计算。 02 的验收要在 alive 真正归还之后，再核对 prefix 内容。 每份 40 页是可缓存的逻辑容量，16 份副本不等于 640 页独立内容。

F

Ticket03：命中 prefix 后恢复与后缀计算

完成标准：B 命中 4096，C 命中 3968，并产生各自正确的完整输出。 两者都分配新的请求 alive，并扣除整槽额度。 prefix 来源页和当前请求 alive 是独立的存储位置。

命中后需要两份不同用途的数据：

操作 数据方向 后续使用者
load_back，原文 op2 prefix → P 原生 HBM P 的后缀计算、完整 Index K 传输
fill，原文 op1 prefix → 本请求 P alive D 的 prompt 主 KV 读取
admit，原文 op3 本请求 P alive → prefix 后续请求的命中

op1/op2/op3 是原文的操作名称，不能当作运行时固定 op_id。 每次真实操作仍由 Main 分配唯一、单调的 op_id。 执行顺序是先 load_back，再启动 fill 和后缀计算。 admit 在请求结束后执行。

fill 和后缀计算可以独立推进。 是否实际并行重叠，需要 NPU 测量证明。 Main 在计划时就分别保护两个操作的 prefix 来源。 load_back 与 fill 各完成一次，各解除一次自己的保护。

B：4096 个相同 token，加 1024 个新 token。

  1. 匹配 A 保存的 32 页，hit_len=4096。
  2. load_back 恢复这 4096 token 到原生 HBM。
  3. 主 KV 按 token 映射拆回 512/64 两部分。
  4. 21 个 producer 层的 Index K 另行恢复。
  5. 构造长度为 4096 的 prefix_indices。
  6. fill 写入 alive 的区间 [0,4096)。
  7. P 只计算并写回区间 [4096,5120)。
  8. 两段及所有必要副本完成，才报告 5120 ready。
  9. D 满足三条件后，正常生成与释放。
  10. 结束时只 admit 新增 8 页，prefix 达到 40 页。

prefix_indices 是逐 token 的原生 KV 索引。 它是逐 token 的 4096 个索引，逻辑和原生各对应 32 页。 若原生 allocator 返回不连续页，复制也必须按真实索引执行。

后缀跟踪器描述 [hit_len,prompt_len)，内部完成计数从零开始。 它不把 hit_len 伪装成已经完成的写回量。 若后缀先完成、fill 仍未完成，ready_tokens 仍不能越过空缺。 D 就绪取决于请求 alive，不等待结束后的 prefix admit。

C：与 A 完全相同的 4096-token prompt。

命中上限是 floor((prompt_len - 1) / B) × B。 因此 C 命中 3968 token，最后 B token（本例 128）仍由 P 重算。 该规则保留原生末段计算和首 token 采样路径。

内容 C 的具体值
DRAM 命中 31 页，即 token 0–3967
HBM 有效内容 31 个完整页
HBM 恢复 31 个页，每页 B=128 token；后缀另用第 32 页
prefix_indices 长度 3968，不包含后续 128 token
重算范围 token 3968–4095，写入第 32 页
结束时 admit 最后一页的 prefix 已存在，跳过；总量仍为 40

“完全命中”表示整段 prompt 已有缓存来源。 本设计仍按上限保留最后一页计算。 DRAM与HBM页边界一致；旧半页接续要求已由统一页决定取代。

P 原生 HBM 在后缀写回和原生传输完成后可以释放。 它不等待独立读取 prefix 的 fill。 但 D 必须等待 fill 和后缀在 alive 中全部就绪。 B 的命中段结束后可先逻辑释放，整槽仍等待新增页 admit 完成。
